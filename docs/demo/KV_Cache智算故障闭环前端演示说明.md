# KV Cache 智算故障闭环前端演示说明

本文用于通过 AgenticSRE 前端演示智算集群的完整故障闭环：正常负载、故障注入、指标观测、事件聚合、Agent+Skill 诊断、受控自愈和恢复验证。

## 演示主线

在 `t4-vllm-k8s` 集群中，先向 `vllm-server / qwen2.5-coder-3b-k8s` 发送低强度正常请求，建立业务基线；随后注入 `sw-003 / KV Cache Exhaustion`。故障负载会根据模型上下文长度生成长 Prompt，并逐步填充 KV Cache。系统通过 vLLM、Prometheus、GPU 和 K8s 证据识别异常，由 Agent 调用 Skill 完成诊断和自愈规划，最后删除故障负载并验证指标恢复。

这个场景不会修改模型权重，也不需要重启 vLLM。恢复动作只删除带标签的 KV Cache 故障负载 Pod，适合作为现场演示场景。

## 演示目标

观众应能清楚看到以下闭环：

```text
正常推理负载
  -> KV Cache 故障注入
  -> KV Cache / 队列 / 时延异常
  -> 智算事件聚合
  -> Agent 选择并调用 Skill
  -> 基于证据确认 KV Cache 压力
  -> 生成最小影响恢复动作
  -> 删除故障负载
  -> 指标与请求成功率恢复
```

重点不是展示一个预设结论，而是展示诊断门禁：只有实际 KV Cache 指标达到配置阈值，系统才确认 `KV Cache Exhaustion`；如果指标未达到阈值，系统应降级为业务性能退化，而不是强行给出高置信度结论。

## 推荐参数

### 正常业务负载

入口：`负载生成 -> 智算负载`

| 参数 | 推荐值 |
| --- | --- |
| 目标集群 | `T4 vLLM 智算集群` |
| 推理服务 | `vllm-server` |
| Served Model | `qwen2.5-coder-3b-k8s` |
| 持续秒 | `600` |
| 并发 | `2` |
| Prompt | `512` |
| Tokens | `32` |
| QPS | `1` |

这组参数用于建立稳定、可观察但不过早耗尽 KV Cache 的业务基线。

### 故障实验

入口：`智算故障实验`

| 参数 | 推荐值 |
| --- | --- |
| 目标模式 | `K8s` |
| 目标集群 | `t4-vllm-k8s` |
| Namespace | `llm-k8s` |
| Deployment | `vllm-server` |
| Service | `vllm-server` |
| Model | `qwen2.5-coder-3b-k8s` |
| 故障场景 | `KV Cache Exhaustion` (`sw-003`) |
| 闭环引擎 | `Agent+Skill` |
| 背景负载 | 关闭，避免与“负载生成”页面的基线负载重复 |

## 现场操作流程

### 1. 建立正常负载

1. 打开 `负载生成`。
2. 切换到 `智算负载`。
3. 选择 `vllm-server` 和 `qwen2.5-coder-3b-k8s`。
4. 按推荐参数填写负载形态。
5. 点击 `启动负载`。
6. 确认“智算运行实例”显示模型名、Service、运行状态和运行实例 ID。

讲解词：

> 系统先从目标集群实时读取推理 Service 和 `/v1/models`，因此这里选择的是实际运行的模型，而不是 Agent 自身使用的诊断大模型。我们先建立一个低强度、持续的正常请求基线。

### 2. 展示正常观测基线

1. 打开 `智算观测`。
2. 选择 `T4 vLLM 智算集群`。
3. 时间窗口选择 `15M`。
4. 打开 `指标曲线 -> 业务/vLLM`。
5. 观察运行中请求、等待队列、成功请求速率、KV Cache、TTFT、TPOT 和端到端时延。

预期画面：

- 请求成功速率大于 0。
- 等待队列接近 0 或保持低位。
- KV Cache 未达到故障阈值。
- TTFT、TPOT 和端到端时延保持稳定。

讲解词：

> 这是故障前基线。后续诊断不仅看故障时刻，还会使用告警前一段时间的上下文，比较基线窗口和故障窗口，避免把长期高负载误判成本次故障。

### 3. Dry-run 和执行预检

1. 打开 `智算故障实验`。
2. 选择 K8s 目标和 `sw-003 / KV Cache Exhaustion`。
3. 闭环引擎选择 `Agent+Skill`。
4. 保持 `Dry-run` 勾选。
5. 点击 `预检`。

预期画面：

- 显示“预检通过”。
- 执行器支持为“是”。
- 阻断项为 `0`。
- 观测模式为 `prometheus_or_vllm_metrics`。
- 命令预览会创建 `agenticsre-kv-cache-load`。
- 恢复预览只删除该故障负载 Pod。

讲解词：

> 真实注入前必须先通过预检。系统会展示作用对象、执行计划、恢复计划和观测信号。这个场景不修改模型权重，也不重启服务，恢复动作只清理故障负载。

### 4. 注入 KV Cache 故障

1. 取消 `Dry-run`。
2. 勾选 `确认真实执行`。
3. 点击 `注入`。
4. 在确认对话框中核对目标为 `llm-k8s / vllm-server` 后确认。

故障注入器会实时读取 `/v1/models` 和 `/tokenize`，根据模型最大上下文长度构造长 Prompt，并使用自适应并发逐步推高 KV Cache，不依赖场景名称硬编码模型长度。

讲解词：

> 这里注入的不是一个静态指标值，而是真实长上下文推理请求。系统根据目标模型运行时信息生成压力，因此同一流程可以适配不同模型和上下文长度。

### 5. 观察故障传播

1. 点击结果区域中的 `查看智算观测`，或切换到已打开的 `智算观测`。
2. 每隔约 10 秒刷新一次，观察 30 到 60 秒。
3. 重点查看以下变化：
   - KV Cache 使用率上升。
   - 运行中请求和等待队列增加。
   - TTFT、TPOT、端到端时延升高。
   - 请求成功率下降或出现请求拒绝。
   - GPU 显存压力和 GPU 利用率变化。

上一次同集群真实验证中，KV Cache 从基线低位升至约 `98.7%`。该数值只作为演示参考，现场结论必须以当前实时指标为准。

讲解词：

> 故障影响首先出现在 KV Cache，随后传播到请求排队和用户可感知时延。系统同时保留目标模型、Service、Pod 和 GPU 证据，避免把其他实例的指标混入当前事件。

### 6. 聚合智算事件

1. 打开 `智算事件`。
2. 选择 `t4-vllm-k8s`。
3. 检测窗口选择 `最近 15 分钟`。
4. 点击 `检测并生成事件`。
5. 找到 KV Cache、GPU 显存压力、等待队列或故障实验相关事件。

预期事件证据包括：

- `cluster_id=t4-vllm-k8s`。
- `namespace=llm-k8s`。
- `deployment/service=vllm-server`。
- `model=qwen2.5-coder-3b-k8s`。
- KV Cache 峰值、等待队列、端到端时延和故障实验运行 ID。

讲解词：

> 事件中心把 Prometheus 指标、故障实验记录、K8s 状态和请求上下文压缩成一个可处置事件。事件上下文严格按集群隔离，不会读取通算或其他智算集群的数据。

### 7. Agent+Skill 诊断

推荐从智算事件详情运行 `Agent+Skill 分析`；也可以回到 `智算故障实验` 点击 `诊断` 或 `Agent+Skill闭环`。

重点展示：

- Agent 读取实时 Skill 目录并选择智算资源压力相关 Skill。
- Agent 通过 Skill 查询目标 Service、Pod、vLLM 指标和故障上下文。
- 输出根因、关键证据、备选假设和置信度。
- 证据门禁比较实际 KV Cache 峰值和配置阈值。
- 诊断结论关联到 `vllm-server / qwen2.5-coder-3b-k8s`，而不是笼统指向整个集群。

讲解词：

> Agent 不直接根据场景名称输出答案，而是调用 Skill 获取实时证据。只有 KV Cache 指标越过阈值，并且目标实例、故障窗口和告警前基线能够对应，系统才给出高置信度的 KV Cache 耗尽结论。

上一次完整验证的参考置信度约为 `0.93`。现场置信度应随当前证据变化，不应固定展示该数值。

### 8. 受控自愈

1. 在诊断结果中查看 `自愈建议` 或 `Agent+Skill闭环` 的恢复计划。
2. 确认建议动作是停止故障负载，而不是重启整个 vLLM Deployment。
3. 回到 `智算故障实验`。
4. 保持 `确认真实执行` 勾选。
5. 点击 `恢复` 并确认。

预期恢复动作：

```text
删除 llm-k8s 中的 agenticsre-kv-cache-load
```

讲解词：

> 自愈遵循最小影响原则。根因是额外长上下文负载占满 KV Cache，因此优先停止故障负载，而不是重启健康的模型服务。真实执行仍经过确认门禁。

### 9. 恢复验证

1. 返回 `智算观测`，持续刷新约 30 到 60 秒。
2. 确认 KV Cache 回落、等待队列排空、成功请求速率恢复。
3. 确认 `vllm-server` Pod 仍然 Ready，未发生不必要重启。
4. 返回 `智算事件`，再次点击 `检测并生成事件`。
5. 确认事件进入观察中或已恢复状态。
6. 返回 `负载生成`，点击正常业务负载实例的 `停止`，完成现场清理。

讲解词：

> 恢复动作执行后还不能立即宣布成功。系统重新采样同一目标的业务指标和运行状态，只有队列、时延、KV Cache 和服务可用性共同恢复，闭环才完成。

## 建议时间安排

| 阶段 | 时间 |
| --- | ---: |
| 场景说明和正常负载 | 1.5 分钟 |
| 正常观测基线 | 1.5 分钟 |
| Dry-run 与预检 | 1 分钟 |
| 真实注入 | 1 分钟 |
| 故障观测 | 2 分钟 |
| 事件聚合 | 1 分钟 |
| Agent+Skill 诊断 | 2.5 分钟 |
| 自愈与恢复验证 | 2 分钟 |
| 总结 | 0.5 分钟 |

总时长约 12 到 13 分钟。

## 现场异常处理

### KV Cache 曲线没有明显上升

1. 确认 `agenticsre-kv-cache-load` 已创建。
2. 等待 30 到 60 秒后刷新 `15M` 时间窗口。
3. 确认目标仍为 `vllm-server / qwen2.5-coder-3b-k8s`。
4. 不要通过手工修改指标或固定结论完成演示。

### 智算事件未出现

1. 确认事件中心选择了 `t4-vllm-k8s`。
2. 将检测窗口设为 `最近 15 分钟`。
3. 再次点击 `检测并生成事件`。
4. 检查 KV Cache 是否实际达到检测阈值。

### 诊断没有确认 KV Cache 耗尽

这是正确的证据门禁行为。应展示当前证据和阈值差距，说明系统不会因为选择了 `sw-003` 就硬编码输出 KV Cache 耗尽。可以继续等待故障负载生效并重新采样。

### 恢复后指标没有立即回落

KV Cache 和排队请求需要一定时间释放。等待 30 到 60 秒，确认故障负载已删除，再刷新观测窗口。不要直接重启 vLLM，除非诊断证据表明服务本身失效。

## 演示结束检查

- `负载生成` 中没有遗留正常负载实例。
- `llm-k8s` 中没有 `agenticsre-kv-cache-load`。
- 没有遗留 `agenticsre-vllm-loadgen` Pod 和 ConfigMap。
- `vllm-server` Pod 为 Ready。
- 基础推理请求成功。
- 智算观测、事件中心和 Agent+Skill 页面仍可正常刷新。

## 一句话总结

> AgenticSRE 不是根据预设场景直接输出答案，而是用真实推理负载制造 KV Cache 压力，通过跨时间窗口、跨数据源且按集群隔离的证据完成 Agent+Skill 诊断，再执行最小影响恢复动作并验证业务恢复。
