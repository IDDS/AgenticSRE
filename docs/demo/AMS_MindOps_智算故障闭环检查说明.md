# AMS MindOps 智算故障闭环检查说明

本文用于下周系统检查和领导演示。目标不是完整讲代码，而是用一条清晰、可验证的智算故障闭环，说明 AgenticSRE 面向 AMS MindOps 运维 Agent 的落地能力：告警聚合、假设验证、置信度评估，以及后续可演进的知识沉淀。

## 一句话主线

当 vLLM 智算集群发生故障时，系统能够从指标、K8S 事件、故障实验、GPU/Trace 证据中自动聚合事件，形成可验证的根因假设，执行诊断与恢复建议，并把置信度和证据过程展示给运维人员。

## 检查重点

领导需要看到的不是“系统有很多页面”，而是四个判断：

1. 智算故障是否真的能注入，并在前端观测到影响。
2. 系统是否能把零散指标和事件聚合成一个可处理的智算事件。
3. 诊断是否不是一句 LLM 结论，而是有假设、证据、验证和置信度。
4. 恢复是否有可执行动作、风险门禁、验证结果，并能沉淀为后续经验。

## 推荐演示路径

### 1. 基线态势

入口：`智算观测` 或 `智算事件闭环`

展示点：

- vLLM 服务、Pod、GPU、Prometheus、TELLER/Trace 采集状态。
- 当前推理请求、等待队列、TTFT P95、端到端时延、GPU 利用率、显存使用率。
- 智算事件中心选择检测窗口，例如“最近 15 分钟”。

讲解词：

> 这里先确认智算集群是可观测的。我们不是等用户报障，而是持续从 vLLM、K8S、GPU 和请求级 Trace 中收集证据。事件中心的窗口可以调整，默认看最近 15 分钟，适合故障实验和在线处置。

### 2. 故障注入

入口：`智算故障实验`

优先选择对 SSH 和集群稳定性影响较小的场景：

- vLLM 进程异常或服务不可用。
- vLLM 请求队列堆积。
- GPU 显存压力或 KV Cache 压力。
- Pod/Service/Endpoint 异常。
- 集群内网络扰动，只作用于业务链路，不影响 SSH。

展示点：

- 从依赖图选择服务、Pod、GPU 或连接边。
- Dry-run 预检展示影响范围、命令计划和恢复计划。
- 真实注入后观察指标变化：请求失败、队列升高、TTFT/E2E 延迟变化、K8S Warning Event。

讲解词：

> 故障注入不是单纯执行命令，而是以拓扑对象为入口。用户可以点服务、Pod、GPU 或依赖边选择故障，系统先做 Dry-run，确认不会影响 SSH 和非目标范围，然后再执行注入。

### 3. 事件聚合

入口：`智算事件闭环`

展示点：

- 点击“检测并生成事件”或开启“实时检测”。
- 系统从多源数据生成统一事件：Prometheus 指标、K8S Event、故障实验记录、Trace 摘要。
- 事件卡片展示严重级别、对象、命名空间、工作负载、模型、指标、阈值、证据。

讲解词：

> AMS MindOps 的第一项关键能力是告警聚合。在线系统不会只有一个信号，通常是多个指标、K8S 事件和用户侧现象同时出现。这里系统把这些信号压缩成一个可处置事件，避免运维人员在多个页面之间手工拼线索。

### 4. Agent+Skill 诊断

入口：事件卡片中的 `分析`，选择 `Agent+Skill 分析`

展示点：

- Agent 接收事件上下文。
- Agent 选择合适 Skill，例如 vLLM 服务不可用、GPU 显存压力、TELLER Trace 诊断等。
- Skill 执行检测、证据查询、假设验证和诊断输出。
- 前端展示：根因、关键证据、置信度、建议动作、Skill 调用细节。

讲解词：

> 这里重点不是让大模型直接猜答案，而是让 Agent 调用运维 Skill 做结构化判断。Skill 负责查询具体证据，Agent 负责编排和归纳，最后给出中文诊断结果和置信度。

### 5. 恢复与验证

入口：事件卡片中的 `自愈`

展示点：

- 默认 Dry-run，不直接改生产。
- 输出恢复动作、风险、审批门禁、验证命令。
- 恢复后重新采样：事件是否消失、指标是否回落、服务是否可用、Trace 是否恢复。

讲解词：

> 恢复不是“一键乱修”。系统先给出受控动作和验证条件。真正执行前有审批和风险门禁，执行后还要通过指标和服务探测确认恢复成功。

### 6. 进化能力

当前演示建议作为“下半年增强方向”展示，不强行作为完全闭环承诺。

可讲内容：

- 将已确认的根因、证据、恢复动作沉淀到知识库。
- 将有效诊断流程沉淀为 Skill 或 Skill 示例。
- 根据误报、漏报和专家确认的诊断正确/错误标签调整诊断规则与校准参数；恢复成功/失败记录只用于调整自动执行门禁。
- 对同类故障形成复用模板，减少下一次诊断轮次。

讲解词：

> 进化不是简单保存日志，而是把一次成功处置变成下一次可复用的知识、Skill 和门禁规则。下半年可以把这部分作为 AMS MindOps 运维 Agent 的持续学习能力。

## 假设验证的价值对比

### 旧三段式：不做假设验证

流程：

```text
故障注入 -> 诊断结论 -> 恢复建议
```

表现：

- 诊断容易停留在“看起来像某类故障”。
- 多个相似故障容易混淆，例如服务不可用、网络阻断、Endpoint 为空、vLLM 进程崩溃都可能表现为 503 或超时。
- 置信度来源不透明，用户不知道是基于多少证据得到的。
- 恢复建议可能过宽，例如直接重启服务，但真正根因可能是 Service selector、NetworkPolicy 或 GPU 资源压力。

领导可感知的问题：

> 结论有了，但为什么可信、为什么不是其他原因、修复动作是否对症，解释不够。

### 新闭环：加入假设验证

流程：

```text
故障注入 -> 告警聚合 -> 假设生成 -> 证据查询 -> 假设验证 -> 置信度评估 -> 恢复建议 -> 恢复验证
```

系统行为：

- 先从聚合事件生成多个候选假设。
- 针对每个假设查询证据，例如：
  - vLLM 进程是否存活。
  - Pod 是否 Ready。
  - Service Endpoints 是否为空。
  - K8S Event 是否出现 BackOff、OOM、FailedScheduling。
  - Prometheus 是否有队列、时延、GPU 显存压力。
  - Trace 是否显示请求在哪一段耗时异常。
- 对每个假设打分，形成排序。
- 输出最高置信度根因，同时保留备选假设和排除原因。

示例对比：

| 观察现象 | 不做假设验证 | 加入假设验证 |
| --- | --- | --- |
| vLLM 请求 503 | 可能直接判断 vLLM 崩溃 | 检查 Pod、Service、Endpoint、进程和日志，区分进程崩溃、Endpoint 为空、网络阻断 |
| TTFT P95 升高 | 可能笼统判断“服务变慢” | 对比等待队列、运行中请求、GPU 利用率、KV Cache、Trace span，定位是排队、GPU 压力还是模型执行慢 |
| GPU 显存升高 | 可能直接建议重启 | 检查 KV Cache、请求并发、OOM Event、模型副本状态，再决定限流、扩容、重启或清理 |
| K8S Warning | 可能只展示事件 | 将事件和业务指标关联，判断是否真正影响推理服务 |

结论：

> 假设验证的作用，是把“看起来像”变成“证据支持”。它降低误诊和误修风险，也让置信度从主观描述变成可解释的评分。

## 置信度评估怎么讲

建议用“证据校准”而不是“模型自信”来讲。完整 RCA 路径使用六因子加权并应用动态上限：

```text
0.18 * raw_confidence
+ 0.18 * hypothesis_factor
+ 0.27 * evidence_factor
+ 0.17 * quality_factor
+ 0.10 * specificity_factor
+ 0.10 * diagnosis_history_factor
```

六个变量的中英文含义如下：

| 公式变量 | 中文名称 | English |
|---|---|---|
| `raw_confidence` | 校准前置信度 | Raw |
| `hypothesis_factor` | 假设分支稳定性 | Hypothesis |
| `evidence_factor` | 多源证据充分性 | Evidence |
| `quality_factor` | 诊断质量评审 | Quality |
| `specificity_factor` | 根因具体性 | Specificity |
| `diagnosis_history_factor` | 历史诊断正确性 | History |

其中历史诊断正确性（History）只使用专家确认的历史诊断正确/错误标签。Skill Runtime 轻量路径使用
`0.35*raw + 0.35*observed_evidence + 0.20*specificity + 0.10*diagnosis_history`。

讲解时重点说明：

- 关键证据命中：例如 Endpoint 为空、Pod CrashLoop、GPU OOM Event。
- 多源一致性：指标、K8S Event、日志、Trace 是否指向同一根因。
- 反证排除：是否排除了网络、配置、资源不足等相似原因。
- 质量与具体性：Judge/Critic 是否要求人工复核，根因和影响组件是否明确。
- 历史边界：恢复验证不反向提高根因置信度，只用于确认处置结果和约束后续自动执行。

讲解词：

> 置信度不是大模型拍脑袋，也不是恢复成功后的倒推分数。模型自报值只是校准前置信度（Raw）先验，系统再用假设分支稳定性（Hypothesis）、多源证据充分性（Evidence）、诊断质量评审（Quality）、根因具体性（Specificity）和经确认的历史诊断正确性（History）进行校准，并对证据不足、证据冲突和人工复核设置硬上限。恢复成功率与根因置信度严格分离，只进入自动执行安全门禁。

## 和 AMS MindOps 的能力映射

| AMS MindOps 能力 | 本系统对应能力 | 演示页面 |
| --- | --- | --- |
| 告警聚合 | 智算事件中心聚合指标、K8S Event、故障实验、Trace | 智算事件闭环 |
| 假设验证 | Agent+Skill 生成候选根因并查询证据验证 | 事件分析弹窗 |

## 建议演示结构

控制在 12 到 15 分钟。

1. 1 分钟：说明智算运维痛点，信号分散、故障传播快、误修风险高。
2. 2 分钟：展示智算观测和依赖图，证明系统有观测基础。
3. 3 分钟：注入一个 vLLM 或 GPU 类故障，观察指标变化。
4. 2 分钟：智算事件中心聚合事件，解释检测窗口和证据来源。
5. 4 分钟：Agent+Skill 分析，重点讲假设验证和置信度。
6. 2 分钟：自愈 Dry-run 和恢复验证。
7. 1 分钟：总结下半年落到 AMS MindOps 的能力。

## 检查前准备清单

- 智算 K8S 集群可访问。
- Prometheus 可查询 vLLM、K8S、GPU 指标。
- vLLM 服务可接受基础推理请求。
- 智算事件中心检测窗口默认设置为最近 15 分钟。
- 至少准备 2 个可演示故障：
  - 一个服务可用性类故障，例如 vLLM 进程/Endpoint/Service。
  - 一个智算特有故障，例如 GPU 显存/KV Cache/请求队列/Trace 时延。
- 所有真实注入必须先 Dry-run，网络类故障不能影响 SSH。

## 推荐领导汇报口径

> 这个系统现在展示的是 AMS MindOps 运维 Agent 的核心闭环：从智算集群故障注入开始，系统自动观察业务和基础设施信号，把散落的指标和事件聚合成统一事件；Agent 再调用 Skill 生成和验证根因假设，给出有证据、有置信度的诊断；最后输出受控自愈计划并验证恢复效果。相比过去只做“注入、诊断、恢复”的三段式流程，假设验证让诊断从经验判断变成证据驱动，能显著降低误诊、误修和不可解释的问题。
