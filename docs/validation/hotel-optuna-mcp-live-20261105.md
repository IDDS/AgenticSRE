# 酒店业务 Optuna MCP 调优实验记录（2026-11-05）

在非生产 Kubernetes 酒店业务上，以 `/hotels` 查询的 P95 延迟为性能指标，比较 rate 服务 CPU 上限从 500m 提高到 1 核。内存和资源请求保持不变；负载通过端口转发，逐请求检查 HTTP 状态及返回条目数。此实验涉及资源增加，不足以将性能变化归因于优化算法。

Optuna MCP 在 8 并发负载下针对 500m、1 核和 2 核完成 6 次建议和评测，每次两轮 8 秒，共 13,909 次计时请求；依据测得的 P95 选择 1 核并冻结。受限宿主执行配置更新、采集和恢复；MCP 报告 `evidence_verified=false`，宿主重算不改变该状态。

随后分别进行 ABBA（基线、候选、候选、基线）对照，每区块 3 轮、每轮 12 秒，各产生 6 组配对：

| 场景 | 计时请求 | P95 改善率中位数 | 吞吐变化中位数 | 恢复后业务检查 |
| --- | ---: | ---: | ---: | ---: |
| 8 并发冻结后对照 | 20,331 | 4.21% | +10.54% | 10/10 |
| 12 并发新场景探索 | 21,429 | 22.95% | +16.91% | 10/10 |

P95 改善率为 `(基线 P95 - 候选 P95) / 基线 P95`。12 并发六组改善率分别为 5.04%、30.15%、42.77%、15.75%、13.92%、41.09%，中位数超过预设的 10%；8 并发结果未超过该阈值。两次试验的逐请求记录及配对计算已在测试环境独立重算，结束后资源配置恢复。12 并发是另一负载下的探索，不能当作 8 并发对照的重复实验。

区块内的轮次共享时段和 Pod，不能视为六次完全独立的随机实验；响应状态和条目数检查不覆盖全部业务语义。此记录证明限定场景下的观测数值，不证明 Agent 自主执行或核验证据，也不构成正式项目验收。原始逐请求数据、复核摘要和报告保存在私有测试材料中。
