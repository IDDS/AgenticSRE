# 持续 HTTP 业务恢复探测

> 后续已完成累计发布，当前状态见 [发布验收记录](recovery-release-20260921.md)。下文保留本阶段验证时的状态。

2026-10-26 的后续增量增加了可选、有界的 JSON 业务响应断言，配置与语义见 [业务响应恢复验证](../business-recovery.md)。本文以下“不读取响应体”等描述保留为旧 HTTP 头部模式的历史范围。

## 已实现范围

在 `/api/heal/execute` 完成基础设施验证后接入服务端配置的 HTTP 探测。
仅基础设施确认恢复，或网络故障清理明确完成且要求业务探测时启动。
每个探测严格匹配 cluster_id、namespace、service，不接受执行请求中的 URL。
配置重复、目标不匹配、配置错误和请求不可达均保持恢复未知。

每次请求检查精确 HTTP 状态码和响应头到达时间；连续全部样本通过才通过。
任意一次非期望状态或响应头过慢立即判定未恢复，不能由后续好样本覆盖。
不跟随重定向，不读取响应体，不使用环境代理或 .netrc 凭据。连接失败和
超时属于证据不可得，返回未知而不是假定恢复。输出保留时间、状态码、响应头
延迟、样本数和实际观察时长，不回显配置 URL 或响应体。

这是短窗口合成 HTTP 请求，不是业务全量错误率、P95 延迟、响应体正确性或
下游全部依赖的验证。探测路径是否能代表真实业务由运维配置负责。

## 配置示例

在服务端 YAML 的 remediation 下配置；地址仅示意，不能直接复制为现场地址：

```yaml
remediation:
  business_recovery_probes:
    - cluster_id: ""  # 空串仅匹配默认集群，不匹配其他集群
      namespace: demo
      service: frontend
      url: http://frontend.demo.svc.cluster.local/checkout-probe
      expected_status: 200
      samples: 3
      interval_seconds: 2
      timeout_seconds: 3
      max_header_latency_ms: 1000
```

使用实际业务路径的只读 GET 探测。样本数 2–5，间隔 1–10 秒，请求超时
0.1–5 秒，响应头延迟阈值 1–10000 毫秒。HTTP 超时是底层连接/读取超时，
不是整个进程的硬截止时间。当前在原请求中执行，没有后台调度或重启续跑。

配置为空保留旧基础设施验证行为，但明确输出 verification_scope=infrastructure，
前端标为“基础设施就绪，业务未验证”。只要启用非空探测配置，目标未匹配
就返回未知；因此启用时应覆盖要自愈的服务。HTTP 通过标为“业务 HTTP 探测通过”。
旧历史记录没有 scope 时保留原显示；本轮不迁移历史成功率。

## 验证与发布边界

远端 snail 隔离容器内运行真实 HTTP 服务，检查连续 200、503、第二次请求失败、
302 重定向、响应头缓慢和连接拒绝。另验证错误集群/命名空间/服务不发起请求、
重复配置、非法阈值、基础设施失败不被业务探测覆盖。API 测试检查探测不可达
时保存待验证记录且不写入知识库成功样本。
