## 真实诊断、自愈与耗时

先创建独立服务并验证业务 HTTP 正常，再执行副本数归零或不存在镜像标签注入。诊断请求只给出当前观测、命名空间和目标，未附带 `fault_type`、`root_cause` 或候选答案；通过集群状态和业务探针判断真实故障及恢复。

| 镜像/场景 | 模式 | 端到端轮询耗时 | 真实结果 |
| --- | --- | ---: | --- |
| 基线：副本数归零 | Agent | 157.28 秒 | 根因正确，`service_disruption`；后续修复建议错误路由到 CPU 类别 |
| 基线：副本数归零 | Agent+Skill | 16.15 秒 | 失败；已取得空 Endpoints 证据，但 Skill 未确认故障 |
| 基线：镜像拉取失败 | Agent | 125.73 秒 | 根因和 ImagePull 类别一致 |
| 基线：镜像拉取失败 | Agent+Skill | 16.22 秒 | 根因和 ImagePull 类别一致 |
| r2：副本数归零 | Agent | 121.24 秒 | 根因文字正确，却输出 `image_pull_error`，审计判定失败 |
| r2：副本数归零 | Agent+Skill | 22.36 秒 | `k8s.service_unavailable` 成功，输出 `ServiceUnavailable` |

这些只是功能样本。Agent 与 Skill 顺序运行并共享隔离知识库，存在学习和运行顺序影响，不能用作独立、公平的性能或准确率基准。镜像故障过程中曾出现仓库连接失败，随后出现标签不存在，只确认 ImagePull 类故障，不据此区分所有拉取失败机制。

r2 Agent 的 `rca-e0043182` 根因为 `spec.replicas=0`、Endpoints 为空，结构化类别却是 `image_pull_error`。原有实验断言只匹配无下划线的 `imagepull`，误将此条标为 passed；本报告覆盖该原始标志，将其判为失败，不修改原始证据。见 [原始结果](../../outputs/system-qa-20261015/candidate-live-results.json) 和 [页面证据](../../outputs/system-qa-20261015/report-fixed-r3.png)。

自动执行门禁发现置信度 72% 低于 85%，正确阻止执行；同时没有得到匹配副本恢复的建议。因此，“自主诊断 → 正确方案 → 自动恢复”未通过，而门禁本身生效。

另一次真实执行实验基于当前 Deployment/Endpoints 事实，经人工确认诊断后，使用故障实验 API 注入、副本恢复、自愈审批、真实回滚和最终清理。13 项均通过，故障 ID 为 `fault-5939ee4d47`，自愈 ID 为 `heal-a08a192f14`。系统内置验证范围是 `infrastructure`；业务 HTTP 恢复由测试侧独立探针额外确认，不能宣称产品已自动配置业务探针。详见 [执行结果](../../outputs/system-qa-20261015/faultlab-heal-results.json)。
