# 告警压缩量化验收：上限压力、反例与在线扫描

## 结论与范围

在远端 `snail` 的现有发布镜像 `agenticsre:job-skill-20260916`（应用代码 `10fe597`）完成 22,624 条受控样本及两次 10,000 条完整 API 验收。所测场景未发现误合并、原文遗漏、critical 级别被隐藏或指标峰值样本丢失。完整回归 **628 passed，102.86 秒**，包含原有 623 项及新增 5 项评分器反例测试。

本轮新增可复用验收程序，没有修改线上压缩算法，也没有更换线上应用版本。压力请求发往独立实例的 18086 端口、使用独立数据目录；线上仅采集一轮当前真实告警快照。测试结束时线上仍为 `10fe597`、healthy。

这些结果证明所列输入的压缩行为符合预期，不能推出生产总体误合并率为零，也不代表原架构所有功能已完成。

## 数据与评分方法

输入由 `eval/alert_compression_acceptance.py` 的固定构造器生成，每条记录有可追踪 ID。预期标签单独保存为 `.labels.json`，不传给压缩算法。标签表示“可合并的通知、日志模板或指标序列”，不是根因真值。数据是受控合成样本，没有将其称为人工标注生产事故集。

误合并按被预测为同组、但预期标签不同的记录对计数；配对召回衡量应合并记录对中实际同组的比例。没有记录对的独立单例场景将 precision/recall 记为 null，不宣称 100% 准确率。评分器使用损坏分组、重复成员、篡改原文、隐藏 critical 等反例验证自身能判失败。

逐条核查原始数据完整相等、每条记录仅出现于一个组、含 critical 的组仍显示 critical，并用固定随机置换验证输入顺序不改变成员划分。每个数据集测量 3 次纯分组时间；这不是稳定 P95 或端到端 SLA。证据包最多检查前 20 个组，报告明确记录抽查范围；指标峰值场景的全部 9 个组均已检查。

## 完整 API 与语义检索边界

使用 `eval/alert_compression_api_acceptance.py` 向独立实例提交两组上限数据，开启实际本地向量检索，关闭 LLM 关系生成，以便单独核查 API、存储和检索的上限行为。

| 场景 | API 耗时 | HTTP 响应字节 | 实际向量索引覆盖 | 结果 |
| --- | ---: | ---: | ---: | --- |
| 10,000 条重复通知 | 3.459 s | 6,754,648 | 100/100 组 | 完整保留，未截断检索 |
| 10,000 条独立告警 | 7.057 s | 17,758,370 | 256/10,000 组 | 完整保留，检索明确 truncated=true |

两次均使用实际 all-MiniLM-L6-v2，候选对不超过 200，没有把候选边标为已确认因果。导入测试数据不进入在线告警生命周期。10,001 条输入明确返回 HTTP 400，并提示 10,000 条上限，没有静默删除尾部记录。

**原始告警完整保留，不等于语义关联完整覆盖。** 当前 256 组索引上限在独立告警场景只覆盖 2.56% 的组；其余组保留但没有进入本次向量候选检索。大规模关联覆盖仍有缺口。17.76 MB 的响应也说明需要后续评估分页或摘要视图，但本轮未更改接口契约。

证据包也不保证小于原文：重复通知场景抽查 20 组对应的原文 487,910 字节、证据包 55,200 字节；独立场景抽查 20 条原文 4,821 字节、证据包 14,761 字节。引用、身份和统计在单例场景有固定开销。所有大小均为序列化 UTF-8 字节，不是 Token 数或磁盘压缩率。
