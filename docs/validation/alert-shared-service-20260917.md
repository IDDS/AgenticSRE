# 共享 Jaeger 服务名的窗口归并优化

## 问题与变化

上一轮窗口协议将 Jaeger `service.name` 限定为 Pod 名。实际部署经常由多个 Pod 使用统一业务服务名，这时即使请求窗口证据完整，也无法通过原映射检索。本次增加可选规则注解 `agenticsre_window_service`，使窗口测量显式映射到所用 Jaeger 服务名；未填写时继续使用原来的 Pod 名约定。

同服务不代表同实体。采集从本次 Kubernetes 清单取得唯一 Pod UID，使用 `service`、`operation` 和 UID 标签检索，返回后继续核验每个服务端 Span 的服务、操作、UID、窗口结束时间。其他 Pod 的请求不能补足当前 Pod 的窗口计数，即使后端忽略搜索标签也一样。Pod UID 缺失或同名清单有歧义、服务名为空/非法、两份测量映射不一致时均不合并。

Jaeger 查询参数的依据是官方 [query_parser.go](https://github.com/jaegertracing/jaeger/blob/main/cmd/query/app/query_parser.go) 中的 `service`、`operation` 和 JSON `tags`。这些参数只用于已配置后端的查询，不允许注解覆盖后端 URL。是否在当前远端后端有效，以实际请求实验为准。

```yaml
agenticsre_window_contract: pod_request_window_v1
agenticsre_window_field: mean_duration_ms # 配对测量为 error_ratio
agenticsre_window_seconds: "10"
agenticsre_window_count_metric: request_window_count
agenticsre_window_end_metric: request_window_end_seconds
agenticsre_window_operation: "GET /checkout"
agenticsre_window_service: checkout
```

证明增加 `trace_service` 和 `pod_uid` 便于审计。历史签名已经包含整个窗口协议，因此不同服务映射不会共享同一模板基线。原始告警、critical、独立测量和非根因声明继续保留。计数、均值重建、全部慢且失败、新鲜度、截断拒绝等门槛不变。

## 验证方法

新增六项共享服务边界测试，覆盖多个 Pod 共用服务名、异 Pod 补数攻击、UID 缺失/歧义、空服务名和映射冲突。远端实际实验使用三个独立 Pod、同一 Jaeger 服务名，各自真实 HTTP 请求和独立指标窗口；每份成功证明必须绑定该分组 Pod 的实际 UID。

运行入口沿用 `eval/window_alert_acceptance.py`，在原有 opt-in 参数之外设置 `AGENTICSRE_SHARED_TRACE_SERVICE=1`、`AGENTICSRE_WINDOW_BOUNDARIES=all`，执行健康、单点、多点、同 Pod 独立请求、缺 Trace、突增、复发与恢复八阶段。关闭共享服务开关时仍可执行原协议回归。

这是受控的实际请求/指标/Trace 验证，不能当作自然生产事故收益。现网此前 17→17 的快照没有窗口协议，本次不通过放宽证据约束或修改业务规则来制造压缩率。

## 实际验收中的失败记录

初次共享服务实验 `6519ea32` 在单点阶段未达 4→1，实际保持 4→2；拒绝原因为 `stale window or unsupported request count`，在进入 Jaeger 查询前拒绝。该轮没有保存伴随指标的具体时间/计数，不能进一步断定是时间偏差还是数量约束，也不能将该轮计为通过。实验已按所有权清理。

随后为候选版本增加有界 `rejection_details`，记录关联分组、求值时间、窗口截止值、年龄秒数和请求数；没有修改任何合并判定或新鲜度门槛。这用于保留后续拒绝现场，避免只凭结果归因。未查明的首次拒绝仍是可靠性限制；即使后续完整轮通过，也不代表该拒绝原因已修复。


## 窗口快照一致性修复

第二次实验 `32d73ebe` 单点两次 4→1，多点首次 9→3、第二次 9→4。失败现场的求值时刻为 `1789694016.846`，窗口截止为 `1789694016.7105708`，年龄约 0.135 秒、请求数 12，实际拒绝原因是均值重建不一致。这次不是窗口过旧，保守拒绝有效。

检查发现原实现从先前范围查询读取延迟/错误率，然后分开查询窗口计数和截止值。即使四项使用相同求值时间，多个查询之间仍可能发生新的抓取提交，使后查询看到此前查询未见的样本。此次改为一个 PromQL 表达式同时读取四项，要求恰好四个字段、同一实体维度、同一求值时间；缺字段、重复字段或混入其他 Pod 均拒绝。

证明中的 `measurement_snapshot` 保存表达式、四个值、标签、求值时间与摘要 ID。均值和错误率重建以这份快照为准；先前范围查询的原始历史点保留，不用新快照覆盖旧证据。已有指标证据 ID 用来绑定原始查询与分组，新的快照 ID 标识实际用于重建的观测。每个候选的伴随指标查询从两次变成一次联合查询。

新增回归测试模拟“同一求值时刻的旧范围样本均值 349、新完整快照均值 350”，要求使用同一新快照完成计数/均值验证，同时保留旧历史点。旧实现应失败，修复版应通过；另增加缺值、重复字段、异实体三项拒绝测试。该测试证明并修复了混用快照的路径；由于失败现场未保存当时四项原始查询响应，不将其断言为那次均值偏差的唯一已证实原因。窗口新鲜度、全量覆盖和 0.01 ms 均值门槛未放宽。


单次快照回归在旧镜像上实际得到 **1 failed / 0.98 秒**（`atomic-red.log`）；最终候选远端全量为 **825 passed / 108.82 秒**（`full-suite.log`）。最终全量含该回归、四值完整性检查以及原有共享服务、窗口、Trace、Skill 与接口测试，存在既有弃用警告。
