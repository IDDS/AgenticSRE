# 假设排除与直接反证验证

此前一次非生产真实缩零故障中，推理模型把“后端不可用”和“selector 不匹配”两个候选标为已排除，引用的分别是无 Pod 和模板标签匹配观测。现有状态更新只要求反驳引用存在；对于没有宿主类型化反证测试的候选，它会接受 `rejected`，而独立审核无法证明这些观测构成同对象、同事故窗口的直接反证，因而阻断整个结论。

本轮在已绑定观测目录的状态更新路径中，将缺少宿主可验证直接反证的排除建议保留为 `proposed_status: rejected`，有效状态保持 `active`，原有置信度、引用和理由保留，并记录 `unverified_rejection` 与待补证问题。独立审核仍将这个待核实的排除意见视为需要审核的断言，不因有效状态变为活跃而放行。重复、缺失、无效或不完整的后续模型更新不能静默清除这个缺口；只有已经注册的类型化测试取得匹配对象的直接反证，才能按现有规则确认排除。未绑定观测目录的旧重排路径不在本轮修改范围内。

直接反证能力目前只覆盖已注册的少量类型化测试；一般自由文本故障机制若没有相应测试，将保守保留待核实状态，不能据此自动排除。引用可解析不等于语义蕴含，模型意见也不是人工审核或动作授权。

对上述真实故障保存的原始推理更新和观测进行无网络、无模型调用的[只读重放](evidence/hypothesis-refutation-replay-20261028.json)：两个原先被标记排除的候选均保持活跃并保留排除建议和证据缺口；独立审核继续阻断。该重放不改变原始调查，也不属于新故障注入或自主恢复。

最终候选在远端无网络容器完成专项回归 635 项、完整回归 2443 项及 JavaScript 语法检查。之后在非生产测试床进行真实缩零：基线业务 20/20 成功，故障期间 0/5 成功，对照请求健康；诊断在 26.711 秒完成，绑定实际注入对象。两项缺少直接反证的候选在实时结果中保持 `active`，原始排除意见和缺口得到保留。
