## 新增探针发现

### 1. 原文保留，诊断摘要仍可能缺失关键峰值

输入同一对象、同一严重度的 20 条日志，大多数为 `upstream response duration_ms=20`，中间第 8 条为 `duration_ms=9000`。这些日志归入同一模板，全部原文仍可读取，但证据包只采样了两条 20 ms 日志，模板中数值被替换为 `<VAR>`，9000 ms 未进入摘要。

原因可以直接定位：`symbolic()` 将显式时延字段视为可变部分；`CompressionStore.dossier()` 取首条、最高严重度代表条和末条，只有结构化 `metric_summary` 才额外保留数值极值。本轮结构化指标对照组正确保留了 9000 ms，说明缺口集中在日志中的数值变化。

这是“提供给诊断的证据是否充分”的缺口，不是原始日志被删除，也尚未证明每次后续诊断都会错误。后续应提取有单位的日志数值与相应记录引用，按峰值、突变和状态变化补充采样，再比较原文与摘要的实际诊断结果。保留 `evidence_url` 不能代替验证诊断流程是否真正补读了遗漏证据。

### 2. 小型中文与跨语言挑战集明显漏召回，扩大 Top-N 未解决

构造 22 个独立对象的文本，其中预先标注 8 对语义相似的正例，另有成功备份、密码修改和证书等干扰文本。标签不传给检索器。正例表示“值得进入后续关联判断”，不表示对象拥有共同根因。

实际 `all-MiniLM-L6-v2` 覆盖 22/22 组，采用精确搜索，无截断、无词法降级。默认 Top-N=5 产生 34 对候选，命中标注正例 **3/8**；Top-N=21 产生 38 对，仍为 **3/8**。

| --- | ---: | --- |
| 英文数据库连接拒绝的改写 | 0.809906 | 命中 / 命中 |
| 中文数据库连接拒绝的改写 | 0.510689 | 遗漏 / 遗漏 |
| 英文与中文数据库连接拒绝 | 0.069453 | 遗漏 / 遗漏 |
| 英文内存超限的改写 | 0.672578 | 命中 / 命中 |
| 中文内存超限的改写 | 0.789787 | 命中 / 命中 |

| 中文存储空间耗尽的改写 | 0.511417 | 遗漏 / 遗漏 |
| 英文与中文无就绪后端 | 0.026980 | 遗漏 / 遗漏 |

当前候选门槛要求同实体、共享本体标签、关键词重合度至少 0.3、或余弦至少 0.55 中的一项成立，再进行 Top-N 排序。本例不同实体之间的五对遗漏未满足门槛，增加 Top-N 无法将其带入后续模型。

这是一组人工构造的小挑战集，**3/8 不是生产语义准确率**，其余候选关系也没有全部标注为正或负，不能计算总体精确率。它足以证明“全部组已向量化”并不保证中文与跨语言的相关告警被召回。

下一步应在固定正负样本集上比较中文词法、本体表达与多语言向量方案，分别统计语言、故障类别和对象范围。扩大词典或降低门槛都需要强反例约束；暂不修改现有生产阈值。证据见 [retrieval-ablation.json](../../outputs/alert-exploration-20261015/probes/retrieval-ablation.json)。

### 3. 导入数据的严重度兼容边界需要补齐

直接导入的记录只包含 `labels.severity=critical`、没有顶层 `severity` 时，归一化结果和分组均为 `warning`。原始标签仍保留，展示级别却降低。

线上 Prometheus 采集适配器会显式把标签严重度提升到顶层，因此本轮没有证明现场采集的 critical 普遍降级。问题是直接导入接入契约：压缩接口接受此记录，归一化时却使用缺省值。应明确顶层与标签的优先级，并对缺失、冲突和未知枚举提供校验或可见提示；同步验证名称、时间和 firing/resolved 字段的来源映射。

### 4. 窗口分组与事件轮次不是同一口径

同一对象在一个导入窗口内出现 `firing → resolved → firing`，当前结果为 2 组，前后两条 firing 属于同组。原文全部保留，但分组没有区分两次触发轮次。

该探针没有调用在线 `AlertLifecycle`；后者有独立的消失确认和重新打开逻辑。因此这里揭示的是导入窗口分组的设计边界，不能据此断言在线生命周期也错误。后续评价需要分别给出“通知分组标签”和“故障事件轮次标签”，避免将同模板压缩率解释为独立事故减少率。

### 5. 真正处理中崩溃可以恢复，调用计数仍不完整

创建 45 对候选的任务，按 20/20/5 分批。第一批 checkpoint 完成、第二批进入可控模型后，仅对测试自身子进程发送强制终止。新工作进程重新取得文件锁和持久任务，跳过第一批，仅重跑第二批与第三批。

最终 45 对全部完成，第一批没有重复，原始记录保持一致，恢复链路通过。但实际进入模型方法 4 次，任务 `model_calls` 为 3：崩溃前在途调用尚未写 checkpoint，没有进入现有汇总。

该计数不是外部服务账单，本轮外部 LLM 请求数为 0。后续需将“尝试开始、响应完成、结果持久化”分开记录，对崩溃中的请求保留未知完成状态。若需费用统计，应再与服务侧实际使用记录对账。

其余新增对照通过：同名对象的容器与租户维度分离为四组；50 次严重度变化在摘要中展示前 20 次，同时明确记录总数 50；结构化指标峰值正确进入证据包。完整结果见 [exploration-report.json](../../outputs/alert-exploration-20261015/probes/exploration-report.json)。

## 后续实验应如何安排

| 优先级 | 工作 | 应观察的指标与验收证据 |
| --- | --- | --- |
| P1 | 修复导入严重度映射与日志峰值采样 | critical 展示保留、关键极值/突变/状态引用保留；反例中不制造或遗漏证据 |
| P1 | 建立中文、英文、跨语言候选基准 | 分类别的候选召回率、每组候选数、强反例命中；候选相关性与共同根因分别标注 |
| P1 | 压缩前后诊断对照 | 原始告警、当前摘要、改进摘要使用相同模型、工具和冻结知识条件；比较完整根因、受影响对象、证据引用与操作建议 |
| P2 | 明确事件轮次与观察窗口 | 覆盖恢复再触发、乱序、迟到、抖动、相同组件的独立故障，分别评分分组与生命周期 |
| P2 | 可靠性与规模补测 | 在途模型超时、硬崩溃、取消恢复、重复提交；不同文本的大量告警、并发健康请求、磁盘/队列增长与调用计数 |

真实数据应区分 Prometheus 当前状态快照、Kubernetes 聚合 Events 和原始通知投递流。只有拿到后者及事件标注，才能评价值班通知减少量；重复采集同一快照得到的条数减少不能代替这一指标。

建立按事故或时间划分的独立留出集，避免同一事故的近重复文本同时进入调参和验收集。优先累计真实事故及“同组件、同时间、不同原因”的反例；没有自然事故真值时，生产误合并率、事件召回率和诊断收益应保持未知。目标应同时覆盖误合并、遗漏高危、证据保留、语义召回和诊断结果，压缩率只占其中一项。
