# 稳定窗口指标下的持续负载对照验证

## 目的和方法

上一轮[请求级指标持续负载实验](alert-sustained-load-20260917.md)出现 4→4、9→9，活动规则匹配和历史时序覆盖均存在问题。本轮使用完全相同的正式压缩镜像 `agenticsre:tracespan-20260917`，改进实验探针的指标表示，检验稳定维度是否能恢复证据采集与嵌套阈值归并。

三个隔离 Pod 持续执行真实 HTTP 请求并发送 OTLP Span 到 Jaeger。探针新增显式 `stable_window` 模式，按实际完成请求计算最近 10 秒的平均处理延迟（毫秒）、HTTP 5xx 比例和请求数。Prometheus 指标只保留 namespace、pod 等稳定标签，不携带每次变化的 trace_id/span_id；窗口指标也不声明 `agenticsre_trace_field`。延迟测量包含实际注入的 sleep，不包含随后的同步 OTLP 导出时间。客户端实测耗时包含完整请求往返。

延迟规则仍为 100/200/300 ms，错误率阈值为 0.5，保留原来的 warning/critical 分级及独立 C 故障。每阶段持续请求 45 秒后扫描两次，扫描期间继续发请求。多出的等待时间覆盖 10 秒窗口转换，再留出系统的 30 秒证据时间窗。

这是探针直接计算的滚动窗口 gauge，不是 Prometheus `rate()` 或直方图分位数的兼容性测试。没有对正式业务埋点、正式规则或 AgenticSRE 运行代码做变更，不能声称已经修复所有生产指标接入。

## 复现

入口 `eval/stable_window_alert_acceptance.py`，复用 `eval/sustained_alert_acceptance.py` 的持续请求与验收，以及 `eval/trace_alert_acceptance.py` 的隔离资源创建和清理。将四份脚本（含 `trace_metric_probe.py`）放到远端现有发布目录，在远端执行：

```bash
AGENTICSRE_RUN_TRACE_ALERT_EXPERIMENT=1 \
AGENTICSRE_RUN_STABLE_WINDOW_EXPERIMENT=1 \
python3 stable_window_alert_acceptance.py
```

需要该目录已有的镜像、配置、Prometheus 二进制以及集群/Jaeger访问条件。脚本不会创建通用生产监控部署。所有临时资源带本轮唯一所有权标签，清理前核验所有权；正式数据目录不挂入实验实例。

## 验收口径

同时验证原始告警唯一分区、critical 保留、不同实体不混并、存储回读一致，且故障扫描的全部指标证据必须 ready。稳定窗口指标不得触发 exact-Span 自动归并，不得把平均值解释为某一次请求的测量。

嵌套阈值子目标为单点 4→2、多点 9→5；原有完整事件目标仍为 9→3，不因子目标通过而降低或替换。没有发生跨指标自动合并，不能据此宣称跨指标归因精度通过。

## 当前实测

六阶段约 316 秒，完成 **1,617 个真实请求、12 次扫描**。实际各阶段负载 **4.13–5.66 RPS**，目标为 6 RPS；单线程请求包含同步 OTLP 导出，实测速率未达到计划值。没有意外请求错误，HTTP 503 均为预期注入结果。扫描耗时 **2.26–5.92 秒**，不是高负载性能上限。

运行编号 `9be7f460`。单点两次 4→2，压缩率 50%；多点两次 9→5，压缩率 44.44%。单点归并后三条延迟规则成为一组、错误率保留一组；多点两个 Pod 各两组，独立 C critical 一组。所有故障测量证据 ready，实际阈值归并执行，模型也取得对应指标上下文；没有 exact-Span 归并。

| 相同故障注入场景 | 每请求变化标签 | 稳定窗口指标 |
| --- | --- | --- |
| 单点故障 | 4→4，0% | 4→2，50% |
| 三个独立故障 | 9→9，0% | 9→5，44.44% |
| 故障复发 | 4→4，0% | 4→2，50% |
| 正常及恢复 | 0→0 | 0→0 |

与前一轮的 0% 相比，结果支持“请求级变化标签是证据链失效的重要因素”。本轮还改变了指标语义和等待时间，因此属于针对问题的工程对照，不是仅改变一个变量的统计因果实验。

故障复发两次均为 4→2（50%）；正常、恢复、最终恢复的六次扫描全部为零告警。模型实际调用六次，全部取得指标上下文；一次复发扫描返回 shared_root 假设，SCAG 在 31 个对齐点上因错误率为常量而给出统计 unknown，关系保持 unverified，人工审核建议为空，没有将假设当成自动归并依据。

全部告警唯一分区、critical、实体边界、存储回读及稳定窗口指标不得触发 exact-Span 归并等断言通过。正式生命周期记录不变，本轮 namespace、两个实验容器及临时凭据配置均清理。脚本 `passed` 指这些子目标通过，不代表完整 9→3 或自然事故验收通过。

证据：远端 `/home/ubuntu/AgenticSRE-releases/tracespan-20260917/9be7f460/`，本地归档 `outputs/stable-window-20260917/stable-window-9be7f460.tar.gz`。归档包含实际执行脚本、扫描结果、请求记录和汇总，不包含平台凭据配置。

## 剩余问题

稳定服务窗口下的跨指标、跨请求事件归并仍未解决。需要明确事件成立的证据、时间演化和同实体独立故障反例；当前既不能仅凭同一 Pod、同时异常或相关性强直接确认共同根因，也不能将单个代表性 Trace 绑定到整段聚合指标。

本轮未覆盖高并发上限、突发流量、Trace 缺失、复杂 PromQL、跨服务传播或自然生产事故标注集。后续[边界实验](alert-load-boundaries-20260917.md)补测了同 Pod 不重叠请求、当前窗口缺 Trace 和实际 16.55 RPS 的负载突增，相关结果单独记录。持续负载的局部压缩有效，不等于全系统压缩率或原设计 1000× 目标达标。
