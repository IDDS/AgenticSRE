# 链路线索驱动的酒店业务 CPU 对照试验

## 试验依据与范围

非生产酒店业务的请求链路涉及 frontend、search、geo、rate、profile 和 reservation。有限链路样本中，search 到 rate 的调用时长在较高并发下上升；对应 rate Pod 的 30 秒 CPU 使用率样本一度约 0.48 核，配置上限为 0.5 核。指标窗口包含邻近流量，链路 Span 包含子调用，且没有 CPU 限流指标，因此这只是人工选择调优对象的线索，不是已证明的瓶颈因果链。

最初尝试两次通过 Pod 原地调整 CPU 上限：服务端预演通过，但实际测试中期望上限变为 1 核后，容器状态在限定时间内仍报告 500m，曾出现 `PodResizeInProgress`。两次均中止、未形成性能配对，并由控制器恢复期望值和报告的实际值；后续观察到 Pod 就绪、无重启、无残留调整状态。不能据此确定底层未生效原因。

## 分块对照与结果

随后在同一非生产应用上，由操作人员将 rate Deployment 的 CPU 上限从 500m 临时调整为 1 核，进行基线—候选—候选—基线（ABBA）四区块对照，每区块三轮、每轮 8 并发闭环请求、预热 3 秒后计时 12 秒。请求经 Kubernetes 端口转发；每轮检查 Deployment 与 Pod 身份、所有权、端点、实际 CPU 限额、镜像、重启次数及返回状态和结果条目数。独立看门狗在控制器失联时尝试恢复原值，实验结束后已恢复原配置，另有 10 次恢复后业务请求通过。

12 轮共 **19,965** 次计时请求，状态和条目数量检查均通过。按事先固定的六组跨区块配对计算，P95 延迟改善中位数为 **6.50%**，吞吐变化中位数为 **+9.40%**；两项数值满足该试验预设的 P95 改善至少 5%、吞吐中位不下降条件。独立脚本从逐请求记录重算 P95 和吞吐，并验证配置及恢复状态，结果一致。此前两次失败未计为有效配对，也没有从本次成功运行中挑选轮次。

这些结果不是正式验收结论：区块内三轮共用同一时段和 Pod，六对数据不具备六次完全独立随机实验的条件；ABBA 只能部分缓解时间顺序影响；端口转发和闭环客户端影响绝对值；响应检查不证明所有业务语义正确；增加 CPU 上限改变了资源配置。配置变更由操作人员执行，不构成 Agent 自主优化。进一步需要测试方确认性能口径、资源约束和业务正确性，并以独立时段复测。
