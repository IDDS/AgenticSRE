## 修复内容与原因

原 `EventAgent` 虽然读取部分 waiting message，却只把状态名称写入模型最终使用的观测目录；同时遗漏初始化容器，以及 `CreateContainerConfigError`、`InvalidImageName` 等状态。kubelet 已经明确报告缺失 ConfigMap 时，模型仍可能只能看见 Pod Pending 这一症状。

[Pod 状态投影](../../agents/pod_state_evidence.py) 现在同时处理应用和初始化容器，保留 reason、原始 message、容器身份、Pod UID、resourceVersion、观测时间及退出状态。展示超过 2,000 字符时显式标记节选，完整 message 留在原始引用中。历史退出记录独立标为 `container_previous_termination`，不会单独充当当前机制证据；恢复后的历史 OOM 不再混写为当前故障。跨命名空间状态被排除，成功退出的初始化容器不作为失败。

首轮完整对照又发现：补齐原文后，机制断言与逐项模型审核已通过，但 EventAgent 的可选长摘要被截断，触发完整性门禁，最终仍要求复核。因此在[告警证据包 RCA 路径](../../orchestrator/rca_engine.py)中直接使用事件原始观测，调查与闭环阶段均不再请求这份重复摘要；普通非告警路径保留原有默认行为。模型响应完整性、精确引用、逐项机制审核及自动动作门禁均未放宽。

## 在线实验协议与隔离

所有构建、pytest、浏览器和集群实验均在 snail。应用基线为 `sha256:806c44ada1056c6c2f3eab21666a1ebf5bf5a72c42bcf92acc2f5c8ef181ea91`；中间候选 r2 为 `sha256:5c184e43416d691ccdf53eeea5791a4df5b4dfeca4153f7f2b153d0cdca43cc5`；最终候选 r3 为 `sha256:9f6322566ad7f2c5c6713c80fdfe0bc27422ed914a4f0639bbe53c510dde3e43`。检索配置显式固定为 `all-MiniLM-L6-v2`。

[实验驱动](../../eval/alert_online_acceptance.py)每轮先冻结 contract、执行顺序、镜像 ID、故障设置及驱动源码 SHA256，再创建带所有权标记的隔离命名空间。三个故障分别为应用容器缺失 ConfigMap、非法镜像名称、初始化容器缺失 ConfigMap，另设健康对照 Pod。通过实际 Pod 状态确认 kubelet 已产生目标状态，再向真实告警 API 导入一条通用 `PodNotReady` 观测，使用存储的 scan/group/revision 引用启动实际 Pipeline。

告警输入只有当前 Pod 未就绪的观测及 UID/resourceVersion，不包含预期根因。故障真值保存在驱动侧，未挂入诊断容器。领域采集器、kubectl、推理和审核均使用真实实现，没有冻结观测替身。[隔离应用入口](../../eval/alert_online_app.py)只在内存中读取只读挂载的模型配置，模型预算为每次 RCA 最多 16 次调用、单次最多 2,048 输出 token、45 秒调用预算及 180 秒 RCA 预算。应用监听回环地址，限制 2 CPU / 4 GiB，使用独立数据目录；恢复、自学习和演化关闭。

本轮检验 Kubernetes 容器启动失败，Prometheus、Jaeger 等观测后端明确不可用。因此这是实时 Kubernetes 取证的完整 RCA 流程，不能外推为指标、日志、Trace 均可用的生产多信号诊断验收。历史 OOM、超长 message、失败退出等补充边界由回归测试覆盖，不能算作新增现场故障。
