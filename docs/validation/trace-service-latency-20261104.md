# 按服务计算链路 Span 时长

在酒店业务预检中，单条链路包含 frontend、search、rate、geo、profile 和 reservation。旧 Jaeger 摘要中的 `total_duration_us` 是整条链路中最长 Span 的时长；TraceAgent 将其用作每个被查询服务的延迟，因此同一条链路可能让多个服务显示相同的整体时长。远程构造回归中，frontend 为 100 毫秒而 rate 为 5 毫秒，旧实现错误地将 rate 记为 100 毫秒。

Jaeger 摘要现在额外返回被查询服务的最大 Span 时长，保留原有整链最长 Span 字段；TraceAgent 使用目标服务的 Span 时长统计，并显式记录无该服务有效时长的链路数量。如果没有有效的目标服务 Span，则返回证据不足，不用整链值或零替代。这个数值是每条链路内同名服务最大 Span 的统计，包含下游等待及子操作，不等于服务独占耗时，也不能单独证明性能瓶颈、SLO 违约或异常因果。

远程酒店平台的只读核验中，查询返回 50 条 rate 相关链路，其中 12 条按 Trace ID 匹配本次有效业务请求。12 条的目标服务最大 Span 时长与事先保存的原始 Span 逐条相等，且均不同于对应整链最长 Span；在该 50 条查询结果中按既有算法计算的服务时长 P95 为 6614 微秒，TraceAgent 的统计一致。50 条可能包含背景请求，12 条只是对应请求验证样本；该统计不是性能优化前后对照，也不证明 5% 提升。

相关远程回归 107 项通过，包括目标服务与整链时长不同，以及目标服务缺失时不能冒充有效服务时长。环境仍缺少可验证的 Span 命名空间属性；Pod 名和 IP 作为进程属性出现，但单靠这些字段不能证明对象归属。真实自主优化和配对压测尚未完成。
