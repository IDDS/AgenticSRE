# 持续负载下的实际告警压缩验证

后续[稳定窗口指标对照](alert-stable-window-load-20260917.md)已完成：持续负载下恢复单点 4→2、多点 9→5 的阈值压缩。本文保留请求级变化标签场景的失败证据，不将后续结果改写为本轮通过。

## 实验范围

在远端 snail 使用已部署镜像 `agenticsre:tracespan-20260917`，通过三个隔离 Kubernetes Pod 持续执行真实 HTTP 请求，经实际 Prometheus 规则触发告警，再调用隔离 AgenticSRE 的实时扫描和存储回读 API。没有向扫描接口注入告警 JSON，也没有修改正式告警规则或压缩实现。

入口 `eval/sustained_alert_acceptance.py` 复用 `eval/trace_alert_acceptance.py` 的资源创建及所有权核验清理流程。必须同时设置 `AGENTICSRE_RUN_TRACE_ALERT_EXPERIMENT=1` 和 `AGENTICSRE_RUN_SUSTAINED_EXPERIMENT=1`。每个 Pod 由一个线程以 0.5 秒间隔发送请求，总目标 6 RPS；故障请求实际延迟 350 ms、返回 503。每阶段先持续请求 32 秒，再在请求继续执行期间完成两次扫描。

这属于低流量、持续请求下的功能验证，不是最大吞吐压测。探针沿用上一实验的最后请求 gauge 和每请求 Trace/Span 标签，不代表常见服务级聚合指标。故障来源为受控注入，不属于自然生产事故。

## 观测结果

运行编号 `6943aa54`，六阶段共约 238 秒，完成 1,213 个真实请求和 12 次扫描。实际阶段吞吐为 4.13–5.66 RPS，低于目标 6 RPS；每 Pod 单工作线程受 HTTP 请求（含同步 OTLP 导出）耗时限制，不将计划速率冒充实际负载。请求执行无意外错误，注入的 HTTP 503 属于预期结果。每阶段两次扫描：

| 场景 | 原始告警→分组 | 压缩率 |
| --- | --- | --- |
| 正常持续负载 | 0→0 | 不适用 |
| A 单点延迟和错误 | 4→4 | 0% |
| A、B 延迟和错误，C 独立错误 | 9→9 | 0% |
| 恢复后持续负载 | 0→0 | 不适用 |
| A 故障复发 | 4→4 | 0% |
| 最终恢复并保持负载 | 0→0 | 不适用 |

已有原文唯一分区、critical 严重度保留、不同实体不混并、同 Span 归并必须同请求、存储回读一致等断言。脚本的 `status=passed` 仅表示实验执行及这些断言通过，不表示压缩收益达到目标。由于没有发生归并，“没有误合并”不能证明有归并时的精度。

## 原因与影响

持续流量不断改变请求标签，而 Prometheus 每秒抓取和求值。扫描中的告警采集与规则证据读取并非同一原子快照。本轮六次故障扫描的 34 份逐组指标记录全部未就绪，分为两个实际观测到的原因：13 份为 `firing rule is missing or ambiguous`、`matching_rules=0`，旧告警引用的请求已经不在随后读取的活动规则实例中；21 份为 `insufficient numeric history coverage`，请求时序的历史覆盖不足。

代码要求同一测量序列至少五个点且覆盖时间窗的 80%，不断变化的请求级时序不满足这个要求。因此仅解决活动规则快照匹配也不足以修复这条链路。8 次实际模型调用均完成，但没有可用指标上下文，也没有返回关系。

因此，上一轮让最后请求值保持约 27 秒的 9→3（66.67%）只能证明静态请求观测场景有效，不能外推持续负载。本轮结果也不能外推为所有稳定标签的生产指标都没有压缩效果。

下一步应使用稳定服务/Pod 维度的请求计数、错误率及延迟窗口指标开展对照实验，将请求 Trace 用作独立证据引用；之后验证跨请求的事件聚合及同实体独立故障反例。不能简单忽略 Trace 标签或放松证据门槛来提高压缩率。突发流量、Trace 缺失、吞吐上限和自然事故标注集仍未覆盖。
