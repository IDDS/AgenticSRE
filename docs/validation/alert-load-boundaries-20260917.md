# 持续负载下的归并边界验证

## 范围

基于[稳定窗口指标实验](alert-stable-window-load-20260917.md)，使用正式镜像 `agenticsre:tracespan-20260917` 在远端 snail 隔离 namespace、Prometheus 和 AgenticSRE 中补充边界场景。新增入口 `eval/extended_load_alert_acceptance.py`，需要同时设置 `AGENTICSRE_RUN_TRACE_ALERT_EXPERIMENT=1`、`AGENTICSRE_RUN_EXTENDED_LOAD_EXPERIMENT=1`。

每阶段先持续请求 45 秒，再在请求持续执行期间完成两次实际扫描与存储回读。原始告警全部保留，critical 不降级，不能跨实体混并。正式运行代码和正式规则不变；本轮实现的是可复现的边界实验，不冒充新增跨指标自动归并算法。

## 场景与验收

**同一 Pod、互不重叠的异常请求。** A Pod 每七次请求包含两次延迟 1,000 ms 但返回 200 的请求，五次快速返回 503 的请求。B、C 持续正常。使用同一 Pod 的 10 秒平均延迟和错误率触发真实告警，窗口内可同时出现两类症状，但不存在同时“慢且失败”的请求。原始请求记录必须验证慢请求和失败请求的交集为空。延迟阈值可因窗口均值变化而触发不同档位，因此验收要求至少延迟 100 ms 与错误率规则同时 firing，并保持延迟、错误率两组，不把固定的原始告警数量当成前提。这验证一个明确反例，不等同于证明所有共同根因均不存在。

**当前窗口没有 Trace。** 三个 Pod 持续执行原来的故障请求，但实际跳过 OTLP 导出。请求响应和日志记录 `trace_exported=false`，生成的 Trace ID 只作请求标识，不能称为已采集链路。Jaeger 仍可返回一小时内的旧 Trace，断言检查扫描时间窗内没有 Span/调用边，不能通过清空或过滤原始证据制造“缺失”。指标证据应保持 ready，同指标阈值压缩仍为 9→5，不能发生 exact-Span 跨指标归并。

**负载突增。** 每 Pod 从一个请求线程增加为四个，计划总速率从 6 增至 24 RPS。按实际完成请求计算吞吐，必须超过正常阶段实测值的 1.5 倍，不能只以线程数或计划速率宣称突增。故障保持 A/B 延迟加错误、C 独立错误，期望 9→5，critical 与实体边界保留。阶段扫描发生在突增后的稳定窗口，未测瞬间突增期间的逐秒告警行为，也不代表吞吐上限。

正常和最终恢复阶段要求零告警。所有阶段均保留实际请求、扫描 JSON 和回读验证结果。资源清理只操作本轮唯一所有权标签匹配的 namespace 和容器。

## 实现边界

这些反例约束后续算法：同 Pod、同时越阈值或同一窗口不足以自动确认共同事件；Trace 采样和历史 Trace 不能当作完整请求集合。跨请求归并需要明确的测量窗口、请求集合覆盖及独立证据，且与“根因已确认”分开表达。

当前探针是受控实验，窗口 gauge 不是通用 PromQL `rate()`/直方图适配。自然事故标签集、跨服务故障传播和完整 RCA 仍未验收。没有为提高压缩率修改正式系统的证据门槛。

## 实测结果

运行 `c4c6d0ff`，五阶段约 **266.64 秒、1,989 个真实请求、10 次实际扫描**，实验及保留断言通过。

| 场景 | 两次扫描 | 实际请求速率 |
| --- | --- | --- |
| 正常负载 | 0→0、0→0 | 5.64 RPS |
| 同 Pod、请求集合不重叠 | 3→2、4→2 | 4.88 RPS |
| 当前窗口没有 Trace | 9→5、9→5 | 4.20 RPS |
| 负载突增 | 9→5、9→5 | 16.55 RPS |
| 最终恢复 | 0→0、0→0 | 5.65 RPS |

同 Pod 反例中，A 实际完成 67 次请求，其中 20 次慢但成功、47 次快速失败，慢且失败的交集为零。不同症状始终保留两组，只有延迟的嵌套阈值被归并。动态窗口使 300 ms 阈值在两次采样中状态不同，原始告警数量随真实 Prometheus 状态变化。

缺 Trace 阶段实际完成 231 次请求、导出数为零。两次 Jaeger 采集均成功返回 live_jaeger 证据，各包含 15 份旧 Span，但扫描窗口内新 Span 为零。旧数据没有触发 exact-Span 合并，阈值压缩依靠完整指标证据保持 44.44%。

突增阶段实际完成 920 次请求，16.55 RPS 为正常阶段的约 2.93 倍，未达到计划 24 RPS，不能把计划值作为实测值。两次扫描均为 9→5（44.44%）。这证明该实测负载水平下的阈值压缩稳定，不证明高并发上限或完整事件压缩达到 9→3。

所有故障扫描的指标证据 ready；六次模型调用全部完成并获得指标上下文，均未返回关系，没有 LLM 跨指标压缩收益。扫描耗时 2.39–5.89 秒。没有意外 HTTP 请求错误，注入的 503 为预期故障。

正式生命周期记录保持不变，本轮 namespace、两个实验容器及临时凭据配置均已清理。验证产物位于远端 `/home/ubuntu/AgenticSRE-releases/tracespan-20260917/c4c6d0ff/`，本地归档 `outputs/extended-load-20260917/extended-load-c4c6d0ff.tar.gz`，包含实际执行脚本、请求和扫描记录，不含平台凭据配置。

远端四份实验脚本语法检查和源代码 diff 格式检查通过，正式主服务及 Skill 服务均 healthy。本轮没有修改正式运行代码，没有重跑全量单元测试，不将本次边界实验表述为全量回归通过。

## 后续优化

上述结果保留为旧版方法的实测基线。后续 [窗口请求集合重建优化](alert-window-merge-20260917.md) 引入显式窗口协议和完整请求集合核验，并在最终远端实际负载验收中达到单点 4→1、多点及突增 9→3；独立请求与缺 Trace 仍按保守规则处理。该改进有接入前提，不替代本报告对原配置的测量结论。
