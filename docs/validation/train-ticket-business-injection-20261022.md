## 已核对的实际业务

远端 `train-ticket` 中运行实际业务服务。已通过 Kubernetes API 读取 UI、站点、
车次、路由接口，并在 `ts-travel-service` 中确认进程为 Java。站点、车次、路由
接口当时分别返回 26、5、59 条记录。这些检查只能证明被访问的只读接口当时可用。

实际前端 `assets/js/index.js` 和服务 `/v3/api-docs` 均使用
`POST /api/v1/travelservice/trips/left`，请求字段为 `startPlace`、`endPlace`、
`departureTime`。前端追加日期的时分秒。先前探针误用了 `startingPlace`，返回空列表；
该结果不能归因于业务故障。当时的错误请求返回原生空列表；2026-10-23 正确请求
实际返回 `status=1`、非空 `data` 的对象。探针兼容两种形状，但只有非空业务数据才
算成功；不能从错误请求的返回形状推断正确查询也一定返回原生列表。

已据此在本地修正 `outputs/train-ticket-injection-20261022/preflight.py`，请求使用实际
车次的始发站和中间站、次日 `00:00:00`。**修正后的请求尚未在远端验证成功。**

## 本轮连接阻塞

原持久 SSH 会话失去响应，SCP 及前置检查命令均以连接错误退出，不能假定上传成功。
随后独立重连和沙箱外重试失败；直接连接当时配置的跳板机 SSH 端口也超时。
该证据把当前访问阻塞定位在跳板机连接阶段，无法据此判断集群或业务是否异常。
原 18107、18109 隧道当前也不能认定可用。

2026-10-23 重试时，一次 SSH 命令成功返回远端时间 `2026-10-23T01:11:17Z`。
随后创建持久连接、SCP 上传、独立 SSH 及直接连接跳板机均收到
`Connection closed`；沙箱外重试也失败。因此当前准确描述是**连接不稳定，尚不能
执行远端验证**，不能简单断言服务器持续宕机，也没有证据确定关闭连接的原因。
本轮已询问接入地址、端口或 VPN 要求是否变化，尚未收到答复。修正后的探针上传
没有成功证据。

本轮没有执行副本缩容、Chaos 资源创建、配置修改或数据库操作，没有在本机运行
应用、测试或构建，也没有 commit/push。

## 已准备但尚未执行的持续探针

`outputs/train-ticket-injection-20261022/observe-business.py` 仅含远端只读观测：

1. 要求成功且不超过 5 分钟的前置检查记录及正确请求字段，否则退出；核对
   namespace UID、`ts-travel-service` Deployment UID 和 generation，与前置检查
   不一致时退出，采样结束后再次核对。前置检查每次启动先使旧成功记录失效。
2. 通过现有业务 UI 入口发送至少 30 笔原生余票查询，逐笔记录非空结果、耗时、UTC
   时间、随机 W3C trace ID；每三笔执行一次站点查询作为对照。
3. 汇总成功率、P95/P99，查询现有 Jaeger 中与这些请求关联的 Trace，并核对返回的
   trace ID，保存服务、
   span、父子引用和有限的状态字段。请求头、任意 tag、日志内容不进入证据文件。
4. 所有 port-forward 进程由探针自己创建；必须收到当前进程的监听就绪消息才允许
   访问本地转发端口，避免误用占用同一端口的其他进程；退出时停止自有进程。
   不执行故障动作。

该脚本尚未在远端执行或测试。成功的查询基线要求全部业务查询和对照成功；探针
还要求发现关联 Trace 及至少两个实际服务，才返回成功。即使全部通过，结果仍明确
标记 `fault_injected=false`、`real_business_injection_accepted=false` 和
`booking_transaction_verified=false`，不能升级为完整预订交易验收。
2026-10-23 仅完成代码静态阅读及 `git diff --check`；后者不校验未跟踪脚本的运行
正确性，不能替代远端测试。

## 下一步及故障验收约束

恢复 SSH 后，先上传并执行修正后的前置检查，再执行持续探针。从关联 Trace 选择
确实被该请求调用的依赖，核对实际 selector、Pod UID、原副本和已有实验。没有
健康基线或依赖证据时不得注入。

首轮只针对实际查询链的一项故障，最长 120 秒、单个明确目标。选定具体机制后，
必须先固定目标、原状态、故障期间业务影响阈值、恢复容差、停止条件和撤销方式；
独立于诊断进程的自动撤销措施必须已具备，不能仅依赖请求线程的 `finally`。
不要为等待模型诊断而延长故障时间。

诊断输入仅包含观测到的症状、时间窗口和真实证据标识；注入目标、命令、预期根因
单独作为验收真值保管。分别评价故障是否实际生效、根因是否正确、证据是否对应
同一实体和时间、恢复是否通过。恢复至少需要连续三个业务窗口成功率不低于 99%，
P95 不高于事先测得基线的 1.2 倍；如目标业务必须采用其他容差，应在故障前另行
记录，不能观察结果后修改。只有查询链完成时，报告范围仍限于查询；完整
“登录→查询→预订→订单”需要独立的业务验证。
