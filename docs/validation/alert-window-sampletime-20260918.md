# 窗口采样时间核验与拒绝原因诊断

## 本轮范围

上一轮保留了一次 `stale window or unsupported request count` 拒绝，但未保存当时的具体时间/计数值，无法追溯唯一原因。本轮不把缺失的现场推测成已解决的问题，而是补齐可复现的采样时间核验和明确诊断。

Prometheus 在某个求值时刻选取各时序最近的可用样本，因此同一查询的输出时间相同并不证明原始样本同步；原始时间需通过 `timestamp()` 取得。依据：[官方查询语义](https://prometheus.io/docs/prometheus/latest/querying/basics/#instant-vector-selectors)、[官方 timestamp 函数](https://prometheus.io/docs/prometheus/3.5/querying/functions/#timestamp)。

在原来的一次联合查询中增加四个 `timestamp()` 分支：四项测量值和四个原始采样时间一起返回。必须恰好八个具备相同实体维度的字段；四个原始时间必须相同，并处于求值时刻前两秒内。证明的 `measurement_snapshot.source_timestamps` 和摘要 ID 绑定这些时间。正常路径仍只有一次查询；下述在途采集分支最多补查一次，历史时序不改写。

拒绝原因分为原始样本超前、过旧、不同步，以及窗口截止超前、窗口过旧、请求数非整数、少于两个请求、超过 200 个请求。诊断记录实际值和允许范围，不再将不同问题压成一个笼统字符串。窗口、计数及均值阈值没有放宽。

## 可复现验证

增加九项测试：三个原始采样时间反例、五个具体时间/计数边界，以及成功证明保留原始时间。旧正式镜像在远端执行三个采样时间反例，实际得到 **3 failed / 1.02 秒**；它只检查求值时间，没有识别这三个反例。失败日志保留为 `sampletime-red.log`。

实际反例通过 `AGENTICSRE_PROBE_SAMPLE_LAG_MS=250` 显式启用实验探针，将延迟指标的采样时间设为比其他三个字段早 250 ms。仍由真实 Prometheus 抓取、规则触发和 API 扫描；两个连续扫描必须保持 4→2，明确报告原始样本不同步。该时间注入只用于隔离实验，正式业务指标与规则没有修改。

正例沿用三个 Pod 共用一个 Jaeger 服务名的八阶段负载实验。每份成功证明额外断言：四个原始采样时间全部存在、相同且新鲜。原文、critical、实体边界、缺 Trace 降级和独立请求拒绝仍是验收条件。


第一版候选（尚未加入在途采集处理）的远端离线全量回归为 **834 passed / 108.39 秒**，包含上述九项新增检查和既有窗口、Trace、Skill、API 测试；存在既有弃用警告。


## 实际采样时间反例结果

实验 `23df5bd0` 完成 **266 个真实 HTTP 请求、2 次扫描**，两次都为 4→2。两次拒绝均为 `window samples are not synchronized`，诊断保留四个原始时间且可见两种不同时间。全部原文、critical、实体边界与存储回读通过，正式生命周期不变，实验资源已清理。这里 4→2 是正确的拒绝结果，不追求错误的 4→1。

第一次扫描的延迟样本时间为 `1789696454.479`，其余三项为 `1789696454.729`，相差 250 ms。第二次扫描的延迟样本为 `1789696459.477`，其余三项为 `1789696458.728`，相差 749 ms：在同次查询中，Prometheus 已为延迟选择了较新样本，另外三项仍取上次样本。这是本轮注入条件下的实际证据，说明只统一求值时刻还不够；它不证明上轮缺失现场的失败属于同一原因。


## 正常负载实验捕获的在途采集问题

首轮正常实验 `925e569b` 在健康、单故障、多故障、独立请求、缺 Trace 阶段通过；突增阶段第一次扫描得到 9→4，未达到预期 9→3，实验判为失败。保留 `before-inflight-acceptance.log` 和失败扫描，未通过重复运行覆盖失败结论。

拒绝为 `request window ends in the future`：扫描求值时间 `1789696861.541`，四项原始采样时间均为 `1789696861.528`，窗口截止时间 `1789696861.5493379`，请求数 44。窗口截止比求值时间晚约 8.338 ms。Prometheus 在发出采集请求前记录默认样本时间，而探针在生成响应时记录窗口截止；扫描时间落在两者之间就可能出现该现象。时序依据：[Prometheus scrape.go](https://raw.githubusercontent.com/prometheus/prometheus/main/scrape/scrape.go)。这是本次现场的解释，不作为缺失现场的历史失败的唯一归因。

修复保留“不得使用未来窗口”的限制。仅在四项样本同步、新鲜但窗口截止晚于扫描时，补查该批样本时间之前 1 ms 的快照，最多一次。补查结果仍须相对于**原始扫描时刻**保持两秒内新鲜，并重新通过全部实体、请求覆盖、均值、失败比例和阈值验证；缺失、过旧或仍超前则拒绝。成功证明记录原始求值时间、被排除的在途快照及 `previous_completed_scrape` 选择原因。其他拒绝不触发补查。

新增三个回归场景：上一批完成且新鲜、相对于原始扫描已过旧、补查仍超前。修复前候选镜像运行这些测试得到 **3 failed / 1.01 秒**，证明测试能检出旧行为；记录为 `inflight-red.log`。探针增加默认关闭的 `AGENTICSRE_PROBE_METRICS_DELAY_MS`，用于真实采集响应延迟实验。


## 修复后验证

最终候选的远端离线全量回归为 **836 passed / 108.46 秒**，比上一正式版本增加 11 项净测试；30176 条警告主要为既有弃用警告。全部测试在 `snail` 执行，没有本地运行服务或测试。

在最终镜像重跑采样不同步反例，实验 `11d8a0e1` 完成 **261 个真实 HTTP 请求、2 次扫描**，两次都为 4→2，准确拒绝不同步样本。原文、critical、实体边界、生命周期与资源清理检查均通过。首次反例 `23df5bd0` 亦保留，不覆盖历史证据。


### 普通负载与实验脚本一致性

实验 `c1733fb4` 完成 **2731 个真实 HTTP 请求、16 次扫描**，八阶段全部通过：单故障/复发 4→1、多故障/突增 9→3、独立请求保持两组、缺 Trace 9→5、健康/恢复零告警。突增实际 16.554 请求/秒，健康基线 5.637 请求/秒。

该轮虽设置 200 ms 延迟环境变量，但现场核对发现 Kubernetes ConfigMap 使用的独立探针副本缺少延迟逻辑，故本报告**只将其计为普通负载验证**，不计入延迟或补查路径覆盖。修正文件同步后，实验额外保存实际 ConfigMap 内的 `probe-source.py`，每阶段检查 Prometheus 三个目标的 `scrape_duration_seconds` 均不少于设置值减 10 ms。原始普通负载日志和扫描保留。

实验 `0ab494e9` 使用已核对的实际探针，在三个 Pod 共用 Jaeger 服务名的条件下完成 **2700 个真实 HTTP 请求、16 次扫描、八阶段全部通过**。每阶段采集耗时断言通过，所记录的 24 个目标采集耗时为 0.716～0.728 秒。突增实际 16.574 请求/秒，健康基线 5.635 请求/秒，约为 2.94 倍。
