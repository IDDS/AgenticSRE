## 工作区中的候选实现

`agents/alert_embeddings.py` 提供三个显式 profile：`all-MiniLM-L6-v2`、`paraphrase-multilingual-MiniLM-L12-v2`、`hybrid-minilm`。源码默认保持旧 profile；本轮候选镜像 Dockerfile 显式启用双路。配置项如下：

| 环境变量 | 含义 / 默认值 |
|---|---|
| `AGENTICSRE_ALERT_EMBEDDING_MODEL` | profile，默认 `all-MiniLM-L6-v2` |
| `AGENTICSRE_ALERT_EMBEDDING_PATH` | 旧模型路径，默认 `/app/models/all-MiniLM-L6-v2` |
| `AGENTICSRE_ALERT_MULTILINGUAL_PATH` | 新模型路径，默认 `/app/models/paraphrase-multilingual-MiniLM-L12-v2` |

双路分别归一化、分别搜索各自向量空间，以两路余弦的最大值进入原排序，仍使用原阈值和 Top-5。大规模检索分别生成有限邻居池后取并集，再执行原作用域、时间和排序逻辑，不把拼接向量当作单一语义空间计算距离。Top-5 的竞争仍可能改变个别候选，不能在验证前声称完全保留旧模型命中。

缓存按模型和路径隔离；切换失败时不使用旧缓存冒充新模型。多语言模型与 tokenizer 加载前验证固定 SHA256。模型缺失、校验不通过或配置未知会显式标记 lexical fallback，运行时不下载模型。双路任一路不可用时当前策略整体退化至词法检索，没有隐藏的单路回退。模型文件按不可变制品管理，替换内容需重启进程。

新增 `tests/test_alert_multilingual.py` 覆盖模型来源、配置缺失、空间隔离、作用域和时间边界、大规模双路查询及上限、切换路径清理缓存、并发重复文本、损坏模型拒绝。r1 的 13 项测试全部通过（1.18 秒），完整回归 1129 项通过、5 条警告（224.67 秒）。旧镜像运行其中模型选择、来源标记的 3 项测试均按预期失败，0 个 collection error。所有回归容器无外网、限定 2 核和 4 GB 内存。

## 负载测试发现的线程瓶颈

首次 r1 负载采用同一 2 核、4 GB 配额，顺序执行两个 profile。10,000 个不同实体、仅两种重复文本，旧模型两次耗时 26.010 / 22.975 秒，双路为 48.216 / 40.236 秒；两者均检索全部组，返回 49,970 对候选，保留原始告警和分组。1,024 个不同文本首次耗时旧模型 344.634 秒、双路 340.684 秒；缓存后分别 1.940 / 3.916 秒。

该首次耗时超过 `enrich_retrieval` 默认 120 秒响应期限。本负载直接调用召回函数，不是 HTTP 超时实测；它揭示了冷启动时发生显式退化的风险。检查容器发现 39 个进程线程及明显 CPU 限流；已有 Chroma ONNX encoder 使用自动线程数，而多语言 encoder 已限制为两个线程。

随后使用同一 128 条文本、相同模型/tokenizer/pooling、同一 2 核配额，只改变旧模型 ONNX session 的线程配置。自动线程编码耗时 39.532 秒，限定 intra-op=2、inter-op=1 后为 6.495 秒；两次输出向量逐元素最大差为 0。完整对照记录为 `thread-comparison.json`，原始向量为 `thread-auto.npy`、`thread-bounded.npy`。

据此在 r2 中为两个模型统一设置有限 ONNX 线程，继续使用原有 tokenizer 和 pooling；同时将原语义验收脚本的维度检查改为每通道 384 维，以支持双路运输用的 768 维数组。相同真实召回对照从 r1 的 92.336 秒降至 r2 的 13.568 秒。这个比较包含初始化、多个不同样本和结果写盘，不能解释为单请求延迟。

r2 完整回归再次通过：1129 项、5 条警告、220.82 秒。原语义验收通过，召回样本命中和对照标签与 r1 一致。相同资源限额下最终负载结果如下，第一次表示对应文本尚未进入向量缓存，第二次复用缓存；1,024 组实验发生在 10,000 组实验之后，不包含首次加载整个模型的时间。

| 负载 | r2 旧模型 profile | r2 双路 profile |
|---|---:|---:|
| 10,000 组、2 种文本，第一次 | 21.224 秒 | 42.936 秒 |
| 同上，缓存后 | 20.122 秒 | 40.584 秒 |
| 1,024 组、1,024 种文本，第一次 | 50.576 秒 | 59.179 秒 |
| 同上，缓存后 | 1.580 秒 | 3.817 秒 |
| 整个负载进程峰值 RSS | 949,688 KiB | 1,788,208 KiB |

两种 profile 都覆盖全部输入组，没有组数或候选数截断，原始告警和分组保持不变。万组负载是 ANN 近似检索，两路邻居池上限分别为 104 和 208，输出均为 49,970 个候选对。不同文本负载的候选分别为 3,505 和 3,491 对：Top-5 竞争会改变集合，因此候选数量不必随双路单调增加。合成负载没有为每个候选标注事故关系，不能用它计算准确率。

线程修复显著降低了不同文本的编码开销，但双路检索仍占用更多内存，并且在高重复万组样本上约为单路耗时的两倍。近五万个候选也意味着后续关系审核可能很昂贵，本轮未执行这些候选的真实 LLM 审核。源码继续默认旧模型 profile，双路只在候选镜像中显式启用；当前证据支持进一步回放评估，不支持无条件切换生产默认。

## 复现入口

本地 `outputs/alert-multilingual-20261015/` 包含下载脚本、两个候选 Dockerfile、原始 `candidate-source.tar.gz` 和线程修复 `r2-source.tar.gz`。在远程同名 release 目录先解压原始源码并执行 r1，再解压修复源码并执行 r2，可复现版本对照；不要把当前 r2 源码当作历史 r1 源码构建。

```sh
python3 /home/ubuntu/AgenticSRE-releases/alert-multilingual-20261015/run-remote.py
python3 /home/ubuntu/AgenticSRE-releases/alert-multilingual-20261015/run-r2.py
```

该脚本按依赖顺序构建候选镜像，在旧镜像复现三个预期失败，再运行新增测试、双路真实模型对照、完整回归，以及旧模型/双路各自的 10,000 组重复文本和 1,024 组不同文本负载。所有容器自动清理、无外网、独立于生产；不部署，不提交代码。

双路结果仍存在明确漏召回：共同作用域挑战中的镜像标签不存在跨语言表达，以及隔离挑战中的英文就绪表达、跨语言内存和副本健康表达。新增对照中的 DNS 和挂载也未命中。共同作用域候选从 34 增至 45（约 32%），但其余候选缺少完整标签，不能直接计算错误率；后续 LLM 关系审核的调用成本和准确率未在本轮真实测量。上线前仍需要客户数据回放和审核效果验证。
