# 备选模型思考参数兼容验证

在一次非生产真实故障诊断中，隔离实例使用 `deepseek-flash`，完整流程出现多次截断并耗尽模型预算，最终报告和独立审核未完成。单次最小请求正常返回不足以证明该模型适合完整诊断。

进一步对同一兼容服务进行无故障合成请求：客户端设置 `thinking=False` 时，旧实现仅对名称以 `deepseek-v4` 开头的模型发送关闭思考的扩展参数，对 `deepseek-flash` 别名没有发送。一次 128 token 请求中，默认调用以长度限制结束；显式发送 `thinking.type=disabled` 后，同样限制下得到完整 JSON。两次请求不足以证明稳定性或确定完整诊断截断的全部原因。

现增加 `llm.enable_flash_thinking_control`，默认关闭。仅当显式启用、实际模型名为 `deepseek-flash` 且调用请求 `thinking=False` 时，发送该扩展；其他模型及未显式关闭思考的调用保持既有行为。该开关要求所配置的兼容服务支持相应扩展，不能假设其他网关支持。远端隔离回归 47 项通过，涵盖默认关闭、显式启用、其他模型和原有 v4 行为。

在同一非生产服务再次真实缩零，隔离实例显式启用该配置：从注入开始约 142.111 秒返回 UID 与目标一致的 Deployment 候选，独立审核有记录且覆盖所有候选。相比前一次 6 次截断、2 次超时，本次记录 2 次截断、0 次超时；两次均为单例，模型输出有随机性，不能据此断言统计改善。由于仍存在不完整响应和调查缺口，诊断为 `requires_review`，自动恢复门禁保持关闭。独立看门狗保护下由控制器回退，恢复后目标与对照业务连续三个窗口各 10 组检查成功；这不是自主自愈。没有修改现有运行实例的模型配置。
