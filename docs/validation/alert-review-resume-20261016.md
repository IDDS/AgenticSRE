## 根因和最终行为

旧 `can_resume` 只看调用、时间及总输入额度是否已经耗尽，不知道下一批完整证据的实际请求尺寸。旧装批只考虑单批上限，因此 3 对候选合在一起超过剩余总额度时，即使 1 对能装下，也不会执行。对单批超限的请求虽会保留原文，但重试入口不能解释其无法推进的原因。

现在每个新批次取“单批上限”和“总输入剩余额度”的较小值；失败 checkpoint 的 offset 和范围保持不变。单个请求装不下时记录具体原因，并继续检查后续候选，使后面较小的证据仍有机会审核。原文完整保留，不通过截掉必需证据使请求过关。

作业保存批次状态、候选数和实际序列化请求字节数，终态查询据此计算 `can_resume`、`retryable_pairs` 和 `resume_blocked_reason`，并重新检查当前截止时间。超出单批或剩余总额度时，前端说明原因并停止提供无效重试；仍存在可重试批次时保留入口。

对于所有模型批次均已成功、但结果写入失败或最后一次调用后取消的任务，恢复动作标为 `publish_result`，按钮显示“重试保存结果”。即使调用预算已耗尽，也允许复用全部成功 checkpoint 完成保存；测试验证恢复没有增加模型调用。

新 `review_outcomes` 表是附加状态表，不保存原文或模型答复。旧的已发布部分结果首次查询时，用既有 prepared 快照和 checkpoint 补充一次尺寸评估，此后读取已保存结果。旧记录补充使用 `INSERT OR IGNORE`，防止并发查询覆盖 worker 刚写入的新状态；取消中的未知请求不会为计算按钮状态而重建全部提示。

## 边界与后续工作

- `retryable_pairs` 表示待审批次中各自能装入当前余额的候选数，不承诺这些批次合计能全部完成；每次真实调用仍需通过总预算预留。
- 尚未生成过请求的中断/模型不可用批次，尺寸可能未知，此时恢复判断是暂定可尝试；真实执行会测量并执行预算限制。
- 失败 checkpoint 的既定批次不拆分；完整批次装不下时保持失败/待审及原始证据。超大证据分块仍需单独设计。
- 输入计量仍为序列化 messages 的 UTF-8 字节，输出为调用前预留 token；尚未接入供应商实际 token/账单计量。
- 跨扫描缓存没有启用。当前任务库没有成功审核 checkpoint，且缺少固定模型/提示版本与审核前事故轮次；具体只读统计和可实施契约见[缓存接入条件](../research/alert-review-cache-readiness-20261016.md)。
- 真实事故的压缩覆盖、误关联、根因质量及等质量成本收益仍需独立 incident/campaign 数据验证，不能由本轮合成回归推断。
