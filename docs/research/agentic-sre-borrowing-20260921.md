# 面向 AgenticSRE 的外部运维智能体调研与借鉴建议

日期：2026-09-21；版本：1.0。面向 AgenticSRE 研发决策与研究评审。
研究对象是当前 **AgenticSRE** 项目，基线为 `3d252a3`；AgenticOps 等名称仅指
外部参考系统。本次为公开资料、论文与代码审阅，未部署或运行外部系统，
未新增本项目故障实验。文中的工作项和验收条件均为建议，不是已实现结果。

## 一、结论

**最值得投入的是恢复效果验证、知识与 Skill 的版本联动，以及可恢复的执行控制。**
现有告警压缩、SCAG、取证和证据评审可以继续复用。外部系统最有价值的启示，
是把每次调查、修改、验证、失败和经验更新连成可追溯的执行过程。

| 判断 | 依据 | 信心与改变判断的条件 |
| --- | --- | --- |
| 补齐业务恢复验收，很可能比继续增加诊断 Agent 更直接改善自愈可信度 | STRATUS 的状态约束；本项目通用验证 Skill 生成检查清单，正式执行入口已有对象状态检查 | 高：缺口有代码依据；若所有入口已有持续业务探针及旁路回归检查，应降为统一接口工作 |
| 知识发布后与执行版本绑定，很可能比单纯扩大知识库更有价值 | Holmes 的运行手册机制；本项目知识审核完成，但专用 Skill 与知识库动作仍未统一 | 高：工程差距明确；实际收益需前后对照 |
| 保留现有架构，逐项引入机制，比整体迁移更适合当前阶段 | 当前已有完整链路及远端证据；外部项目本身也存在版本、权限和取消语义边界 | 中高：若今后必须支持多租户、多写者及跨地域执行，再评估平台替换 |
| 当前受控实验通过，仍不足以推断自然事故准确率 | 本项目验收范围；AIOpsLab、ITBench 的任务化实验设计 | 高：需独立标注、多故障与不同负载试验才能改变 |

这些是基于证据的工程判断，不是外部平台之间的性能排名。

## 二、调研范围和方法

回答五个问题：哪些方法有可查实现；如何处理执行失败及效果验证；如何更新知识和
Skill；与本项目现有能力有什么差距；优先做什么、如何证伪其收益。

核心样本为 STRATUS、HolmesGPT、Azure SRE Agent、AWS DevOps Agent、
LiboMa/agenticops-chat、kagent，以及 AIOpsLab、ITBench 两套评测框架。
StackStorm/Orquesta 作为确定性工作流参照。这里的 AgenticOps 指运维智能体系统，
不把同名的 Agent 观测 SDK、编程助手工作流产品混作直接竞品。

证据分为：正式发表论文、arXiv 修订稿、公开源码、官方产品文档、本项目实现与
内部验证记录。公开源码能证明相应路径存在，不能证明实际环境可靠；官方产品
说明也不等于独立效果测评。本报告不采用厂商宣传的 MTTR 或准确率作为选型依据。
文档和论文描述冲突时保留差异，以具体版本、具体调用路径为准。

## 三、外部系统中可借鉴的机制

### 1. STRATUS：把修复视为有条件提交的事务

STRATUS 是 NeurIPS 2025 发表的多智能体 SRE 系统，提供公开实现。其 TNR
设计将修改前状态、执行结果和撤销操作纳入确定性控制；写操作排他、准确撤销和
有限操作窗口是关键前提。它的事务边界性质不等于过程中用户完全不受影响，也不
能直接推广到不可撤销的外部副作用。[论文与发表信息](https://papers.nips.cc/paper_files/paper/2025/hash/47a6e9e2c3019f13ad94a0f259fe4970-Abstract-Conference.html)、[代码](https://github.com/xlab-uiuc/stratus)、[2026 年 arXiv 修订稿](https://arxiv.org/html/2506.02009v2)。

**本项目建议：**在现有执行日志和回滚机制上，统一增加 `pre_state`、`post_state`、
`business_verdict` 和 `rollback_verdict`。恢复对象配置不等于业务恢复；回滚命令
退出成功也不等于恢复到了预期状态。先覆盖可逆的声明式资源操作，再讨论扩大范围。

### 2. HolmesGPT：运行手册参与取证，模型能力也做回归

Holmes 根据问题匹配运行手册目录，再通过 `fetch_runbook` 加载步骤，报告完成或
跳过的检查。其公开评测按难度、回归和工具类型组织案例，支持多次运行；配置还
标注可能泄漏答案的案例和工具能力限制。[运行手册](https://holmesgpt.dev/0.23.0/reference/runbooks/)、[评测方法](https://holmesgpt.dev/latest/development/evaluations/)、[测试标记实现](https://github.com/HolmesGPT/holmesgpt/blob/master/pyproject.toml)。

**本项目建议：**把自愈知识从描述和命令集合升级为有明确前置条件、取证步骤、
修复步骤和验收步骤的版本化过程；UI 展示每一步实际证据与跳过原因。编写了
检查步骤、执行了检查、检查证明恢复，应分别记录。

### 3. Azure SRE Agent：区分经验、用户知识和操作技能

官方文档区分历史事件、用户记忆和知识文档，并说明同一资源的历史优先检索、
成功和失败路径保存、来源引用。Skills 将过程说明与相关工具结合并按需加载。
这些属于产品文档描述，本次未验证其后台学习或权限实现。[Memory & Knowledge](https://sre.azure.com/docs/concepts/memory)、[Skills](https://sre.azure.com/docs/concepts/skills)。

**本项目建议：**沿用已有正负规则和环境指纹，增加知识的适用版本、资源范围、
最后验证时间和失效原因；用户确认的知识与模型总结分开。优先召回同一资源的
已验证经验，但不能因“同一资源”就忽略版本或拓扑已经变化。知识审核通过后，
也不能直接继承上一版本策略的成功率。

### 4. AWS DevOps Agent：把新告警接入正在进行的调查

其当前文档描述了事件分诊、关联已有调查、向运行中的调查补充信息，以及可展开
的子任务时间线。另一份当前文档支持需显式开启、限定操作和资源、并在执行时
审批的 directed actions。不能再一概沿用早期“只生成计划不执行”的描述。
[事件调查](https://docs.aws.amazon.com/devopsagent/latest/userguide/production-operations-autonomous-incident-response.html)、[定向执行](https://docs.aws.amazon.com/devopsagent/latest/userguide/working-with-devops-agent-working-with-directed-actions.html)。

**本项目建议：**在现有告警生命周期之上增加“调查实例”关联：同一事故的新告警
进入已有证据包，并触发必要的假设更新；无关告警保持分离。前端展示新增了什么
证据、为何合并、是否改变根因判断。工具批准应绑定目标、参数、有效期和执行版本。

### 5. AgenticOps：统一信号入口与可恢复的知识归档

本次固定审阅 `LiboMa/agenticops-chat` 提交
`d5ff2723e5e1b18b2c6bd6f09d4a89ada00347ab`。`signal_gate.py` 将输入事件保存为
可审计信号；规则先判断，灰区模型只能选择合并或新建，不能自行判定噪声。
`curator.py` 实现 active→stale→archived，人工知识不自动归档，但仍可能变为
stale。因此不能把“人工内容受保护”理解成永远参与检索。
[信号入口源码](https://github.com/LiboMa/agenticops-chat/blob/d5ff2723e5e1b18b2c6bd6f09d4a89ada00347ab/src/agenticops/services/signal_gate.py)、[知识整理源码](https://github.com/LiboMa/agenticops-chat/blob/d5ff2723e5e1b18b2c6bd6f09d4a89ada00347ab/src/agenticops/memory/curator.py)。

**本项目建议：**复用已有原始告警保留能力，把 Webhook、扫描和人工导入的处理
决定统一记录；支持误合并拆分和重新提升为独立事件。知识过期应先退出自动使用，
保留原文、审核和使用历史，以便恢复及比较。

其执行看门狗使用线程等待，超时后更新失败状态；审阅的这一路径没有终止工作
线程。因此不应复制成“超时已取消”。[执行服务源码](https://github.com/LiboMa/agenticops-chat/blob/d5ff2723e5e1b18b2c6bd6f09d4a89ada00347ab/src/agenticops/services/executor_service.py)。

### 6. kagent：审批是可暂停、可恢复的任务协议

kagent 1.x 将审批配置在 MCP 工具绑定上；需要用户参与时任务进入
`INPUT_REQUIRED`，客户端响应后继续。同页明确客户端支持不同，CLI 不能完成
该暂停的交互。是否声明审批和是否真正能走通审批，是两个问题。
[HITL 官方文档](https://kagent.dev/docs/kagent/1.x/agents/human-in-the-loop/)。

**本项目建议：**对前端、HTTP、独立 Skill Runtime 的审批恢复协议做统一测试。
保存等待点、精确动作和资源版本，重启后可以继续；版本已变化则使原批准失效。
不要让某个客户端缺少恢复能力时悄悄转为自动执行。

### 7. AIOpsLab 与 ITBench：借鉴实验基础设施

AIOpsLab 提供应用环境、故障注入、负载、遥测和 Agent 交互接口，适合把既有
实验整理成可重复任务。ITBench 提供 Kubernetes 场景及参考 Agent，并有正式
ICML 2025 论文。它们是评测框架，不能当成“可直接替换 AgenticSRE 的产品”。
[AIOpsLab](https://github.com/microsoft/AIOpsLab)、[ITBench](https://github.com/itbench-hub/ITBench)。

**本项目建议：**保存测试独立的故障真值、环境与负载快照，允许同一任务接入
现有多智能体、单 Agent 和规则基线。按检测、压缩、定位、因果解释、修复、
恢复六层计分。修复成功不自动意味着因果解释正确，单元测试通过也不代表模型
在实际事故中表现达标。

### 补充参照：StackStorm / Orquesta

Orquesta 提供任务图、暂停恢复和从失败任务重新运行；取消工作流会停止调度新
任务，但允许已经运行的任务完成。这正好说明取消、终止和撤销不能混用。
[工作流操作文档](https://docs.stackstorm.com/orquesta/operations.html)。

建议借鉴状态语义，暂不引入整套 StackStorm 依赖。未知结果的写操作先核对实际
状态，只有确认未执行或具备可靠幂等性的操作才允许重试。

## 四、与本项目的真实差距

以下是当前代码和既有验证记录的核对结果，不能理解为本轮重新测试了这些功能。

| 领域 | 已有基础 | 应补齐的部分 | 本项目证据 |
| --- | --- | --- | --- |
| 压缩与可信诊断 | 原始输入保留、拓扑/Trace、SCAG、结构化证据评审；受控三服务通过 | 多故障和自然事故标注；调查持续接收新证据；误合并反馈闭环 | [最近 RCA 验收](../validation/rca-evidence-judge-20260921.md)、`agents/alert_lifecycle.py` |
| 自愈恢复检查 | 正式入口检查 rollout、Pod、Endpoint；部分操作明确返回 business_probe_required | 统一业务探针、持续观察窗口和旁路退化检查；验证输出绑定策略版本 | `web_app/app.py::_verify_heal_recovery`、`skill_runtime/skills/generic_recovery_verifier/skill.py` |
| 知识更新 | 草稿、哈希审批、历史恢复、服务器绑定审核身份 | 专用 Skill 与知识库动作统一；发布版本专属验收；独立审核角色 | [知识发布验收](../validation/knowledge-publish-20260921.md) |
| 记忆治理 | 正负规则、过期/冲突报告、动作及环境指纹 | 明确知识生命周期；失败经验的适用范围；过期知识退出执行并可恢复 | `memory/context_learner.py`、`memory/fault_context_store.py`、`remediation_history.py` |
| 失败处理 | Skill 阶段进程终止、失败可见、outcome_unknown 禁止自动重放；已有部分持久化恢复 | 外部工具结果核对、整个工作流恢复、跨入口去重、注册加载隔离 | [Skill 超时边界](../validation/skill-deadline-20260920.md)、[部署记录](../validation/deployment-20260920.md) |

尤其需要区分：`generic.recovery_verifier` 的 `status=ok` 表示生成了验证计划，
不表示它已测量业务恢复；而正式 `_verify_heal_recovery` 已有真实对象检查。
建议统一两者的结果契约，不应误报成整个系统“完全没有恢复验证”。

## 五、建议落地顺序与验收方法

### P0-1：统一恢复效果验证器

把 `execution_status`、`recovery_status`、`regression_status`、`rollback_status`
分开。每次执行保存动作版本、目标 UID、前置状态和实际观测。配置对象就绪只是
一项检查，还应根据服务定义检查实际请求成功率、尾延迟及相关下游健康。

**验收：**制造“命令退出 0 但服务仍报错”“Pod Ready 但依赖失败”“短暂恢复后
复发”“本服务变好但下游变差”等场景。它们都不能直接归为恢复成功。观察窗口
和阈值按业务规定，不把固定等待时间当作恢复证据。缺测量返回 unknown。

### P0-2：知识、Skill、执行计划使用同一版本身份

建议形成 `recipe_id + recipe_content_hash + skill_version + environment_scope`
的绑定。现有审核流程继续保留；审核后进入待验证，执行、效果统计和回滚都记录
该绑定。知识改变影响哪个 Skill、当前哪个版本在生效，应能从 UI 查询。

**验收：**编辑知识后，旧的待审批动作不能误执行新内容；重启后仍指向相同版本；
新版本不继承旧版本成功率；回滚知识后仍需核对当前环境。优先选三类现有自愈
策略打通，再扩大覆盖，而不是一次重写全部 Skill。

### P0-3：把未知结果核对纳入持久化执行状态机

沿用已有执行日志，增加 `prepared → executing → verifying → committed` 和
`outcome_unknown → reconciling → rolled_back/manual_review` 等明确状态。
服务端持有动作幂等标识、资源范围和执行所有权；动作完成但响应丢失时先查
目标状态，不能仅因超时重新派发。资源锁用于防止两个计划同时改同一目标。

**验收：**在调用前、远端已执行但本地未记账、验证中、回滚中分别终止进程；
恢复后没有重复写入，不跳过待验证步骤。已批准但资源版本变化的动作拒绝执行。
无法可靠撤销的动作保持人工控制，不承诺通用 exactly-once 或任意副作用回滚。

### P1-1：建立独立模型与系统评测集

先以 AIOpsLab/ITBench 的任务结构整理现有远端实验，统一环境初始化、负载、
注入、真值、清理和评分接口。最小建议为 6 类故障 × 2 种负载 × 每场景 5 次，
即每版本 60 轮；当前版和候选版合计 120 轮。另设健康、恢复、缺 Trace、相似
但无关告警、迟到事件、超时和日志注入负例。**这是拟议实验规模，尚未执行。**

按故障家族划分开发与保留集，避免提示词针对答案优化。每次输出压缩率、关键
告警保留、误合并、根因 Top-k、正确拒答、恢复成功、回滚成功和越权/重复写。
多次重复用于稳定性，不能伪装成更多独立事故。统计恢复耗时必须按成功/失败
分别报告，不能只统计成功样本，也不能简单与厂商宣传 MTTR 比较。

### P1-2：从单次压缩扫描扩展到持续调查

将相关的新信号关联到当前调查，保存关联理由、原始证据和更新时间，必要时使
旧假设或待执行计划失效。允许人工拆分误合并事件，并记录为有范围的反例。

**验收：**一个故障触发多个不同阈值告警时形成一个调查实例；两个同时发生但
无因果关系的故障不合并；恢复后再发生创建新 episode；迟到告警不错误关闭或
重开当前故障。压缩减少通知不应丢失故障类型、影响面或关键原始记录。

### P1-3：补齐变更证据与可解释前端

在已有拓扑/Trace 上关联发布、镜像版本、配置、扩缩容及操作者审计，区分
“时间上邻近”和“经过验证的触发关系”。前端为每个结论展示：来源、时间、
适用资源、支持与反证、验证状态；为每个动作展示：批准内容、结果、观测窗口、
回滚与未知状态。这比再增加一个汇总面板更便于实际值班使用。

**验收：**两个相邻发布只有一个相关时，不因时间近就确认根因；发布回滚成功
但错误率未恢复时，显示“动作完成、业务未恢复”，保持事件开放。

## 六、替代方案、限制与不宜照搬的做法

**整体换用外部平台**可以减少部分连接器开发，但迁移现有告警语义、知识审核、
实验工具和历史记录的成本尚不清楚，公开资料也不能证明在我们的场景中更可靠。
目前优先复用机制；若跨租户隔离、可扩展执行或长期维护成为主要限制，再做
同一保留集上的替换试验。

**继续优化模型或增加更多 Agent**可能改善难例，但当前已验证的薄弱点包括
执行结果核对、版本生效和恢复验证，单靠模型很难消除。若后续故障分析表明
工具和控制流程稳定、失败主要来自推理，再把模型选择与协作拓扑优化前置。

不要直接照搬几个默认行为：

- STRATUS 的假设不适用于所有云操作，不将其表述成无条件、全过程零退化。
- AgenticOps 的线程超时标记不等于终止外部动作；保留本项目的未知结果语义。
